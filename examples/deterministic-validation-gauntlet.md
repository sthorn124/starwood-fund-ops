# Worked example: a deterministic validation gauntlet between an agent's proposal and execution

This is the governance counterpart to `examples/agent-eval-walkthrough.md`. That example proves the agent behaves; this one makes its output safe to act on regardless. It is the worked example behind `reference/patterns.md` §6 (agent decides, deterministic code disposes and verifies) and §7 (guard patterns). The application's names, the client, and every identifier are removed; the counts and the incidents are as recorded.

## The principle

**The agent proposes; deterministic code validates, disposes, and verifies. The agent never writes.**

The setting: a plan-assembly agent reads a client's handover documents — a prose response and a structured matrix — and proposes a project plan. It may select only from a maintained task library of 52 rows, decide which rows are kept and which are not applicable with a stated basis, group the client's funds into waves with live dates, and propose parameter changes the documents justify. It never invents plan content. Everything on the other side of that seam is deterministic: a gauntlet of checks, the application of a passed proposal into plan rows, a diff of the proposal against the standard plan, the review screen where a human approves it, and the launch that writes it.

The architecture treats the model's output as an untrusted proposal, not as an instruction. That separation is the governance story, and it was arrived at the hard way: an earlier design had let "the thing the tooling can build" define the architecture and re-implemented, badly, what the platform's agent product already provided. The correction was to build the agent in the product and spend the effort on the deterministic layer no product provides.

## The shape of it

1. **The seam** is one expression rule that returns the agent's output as raw text and nothing else. It does not parse, validate, or interpret; a mode parameter selects the live agent or a recorded proposal, and both return through the same path.
2. **The gauntlet** takes that text and runs sixteen checks, each fatal, each returning a value rather than throwing, each naming the first thing wrong rather than all of them. It returns a map: ok, the failed check, the failure reason, every check with its pass/fail and detail so the review screen can show its work, and the parsed proposal.
3. **Application** turns a passed proposal into plan rows in the same shape the deterministic path produces, plus three keys: wave number, decision, rationale. One shape, two producers, so every downstream screen has one implementation.
4. **The diff** presents the proposal as deviations from the standard plan for the project type: exclusions with their quoted basis, instantiation counts, conditional blocks, parameter changes. There is deliberately no "additions" section, because the baseline is all-inclusive and an additions section would imply the agent can author content.
5. **Review** shows the diff with each deviation's rationale, the provenance line ("proposed by the agent from N uploaded documents, verified against the library, 16 checks"), and the same grid, filters, remove, restore, and launch controls as the standard path. The difference between the paths is who drafted the plan, not what the human can do about it.
6. **Launch** writes the rows, and the confirmation counts are read back from what landed.

## The sixteen checks, by class

Each class below names its representative check and the incident that put it there; check labels are the gauntlet's own, generalised where one carried the build's vocabulary. The order is the order they run; the first failure stops the run.

| Class | Checks | Representative check and what it catches |
|---|---|---|
| **Structure** | 1 `PARSE`, 2 `SHAPE` | The text is JSON that can be read, and the three required arrays are present. The agent returns JSON preceded by prose regardless of instruction, so everything before the first brace is discarded first; a parse failure is a normal outcome that routes to the standard plan, never a broken screen. |
| **Reference integrity against the content source** | 3 `WHITELIST`, 4 `COMPLETE`, 5 `DECISIONS` | Every task id the agent returned exists in the library; there is exactly one decision per library row, none missing and none invented; every decision is one of the two allowed values. `WHITELIST` catches invented ids and `COMPLETE` catches dropped rows — together they are stronger than either alone, because an agent that silently omits forty rows passes a whitelist trivially. `COMPLETE` is the "never additions" rule made mechanical. The library is queried inside the gauntlet, not passed in, so a caller cannot supply a permissive whitelist. |
| **Structural consistency of the proposal** | 7 `WAVE_REFS`, 8 `SCOPED` | Every wave a task references was proposed; every kept wave-scoped task is instantiated in some wave, and no case-wide task is assigned to one. `SCOPED` checks both directions, because a kept scoped task with no wave drops work silently and a case-wide task in a wave duplicates it — checking one direction leaves the other failure invisible. |
| **Reconciliation against the extracted source data** | 9 `FUND_COUNT`, 10 `AUM` | Converting funds plus declared exclusions account for the whole matrix, with no fund in two waves and none both converting and excluded; converting AUM plus excluded AUM equals the extracted total. A plan may convert fewer funds than the matrix lists; it may not do so quietly. |
| **Evidential obligation — every claim names its source** | 6 `QUOTED`, 11 `PARAMS`, 13 `FLAGGED`, 14 `EXCLUDED_FUNDS` | A not-applicable decision carries a rationale; a parameter change names its source (the documents or the library) and states its new value as digits alone, and a document-sourced change quotes the verbatim sentence *containing* that value; a flagged requirement states the requirement, quotes the document, and says why no library row can satisfy it; an excluded fund names itself and quotes the sentence that excludes it. `PARAMS` exists because parameters were the only output category with no evidential obligation, and the agent behaved exactly as that gap invited: it asserted a **35-day** parallel period against a document sentence that says **45**, and omitted a **30-day** post-go-live period the same document states. The check is a substring test — the number must appear inside the quoted sentence — so an agent that quotes the right sentence and writes the wrong number fails on arithmetic rather than on anyone's judgement. |
| **Verbatim verification against the uploaded documents** | 12 `QUOTE_VERBATIM` | Every quote, wherever it sits, appears as a substring of the text extracted from the documents the user actually uploaded — compared with all whitespace removed, because a PDF has no sentences, only positioned glyphs, and a whitespace-preserving comparison would reject genuine quotes, which is how a check like this gets switched off within a week. It exists because check 11 cannot ask whether a quote is *real*: a run passed check 11 with a sentence it had shortened, dropping the document's trailing clause and substituting a full stop, in a field whose whole purpose is that a project manager may repeat it to the client. Quote laundering is closed by construction rather than by asking nicely: an invented sentence, a shortened one, a merged one, and a paraphrase all fail the same way an invented task id fails. The agent and the checker read the same extraction, through one shared rule, so they cannot disagree about the characters. |
| **Internal self-consistency** | 15 `AUM_PER_WAVE`, 16 `SCHEDULE` | Each wave's stated total equals the sum of its own funds' figures from the matrix, every fund id exists in the matrix, and each excluded fund's figure matches its row; no wave's parallel run starts before the previous wave's live date plus the post-go-live support period in force — a floor derived from the library's own duration for that task, overridden by any parameter change naming it, found by name rather than by a hard-coded id so a renumbered library cannot silently disable the check. Both exist because a three-run consistency test found two defects that passed all fourteen earlier checks: one run stated wave totals of 8,220 / 23,580 / 15,510 against true totals of 8,910 / 25,150 / 13,250 — the three summed to the correct 47,310, so the summing check reconciled, while wave 3 was overstated by 17 % on the wave carrying every derivatives fund; and two runs asserted that a wave's parallel overlapped the previous wave's support period when the actual gaps were 39 and 4 days. Nothing external was misquoted; the output disagreed with itself, and no reader could see it without recomputing. |

The principle the last class established, stated once in the rule's header and binding every check added afterwards: **the gauntlet binds the agent's claims against the documents and against its own output's internal consistency. A number the proposal contradicts is as inadmissible as a sentence the document does not contain.**

## What happens when a check fails

- **A failed gauntlet is a normal outcome, not an exception.** Every check returns a value; nothing throws. The wizard renders "the agent's proposal could not be used, here is the standard plan instead", names the failing check and its reason in a message a project manager can act on, and the copy says that the fallback is correct behaviour rather than a failure. An exception would have been a broken wizard.
- **Nothing downstream runs.** Application, diff, review, and launch are gated on `ok`. A rejected proposal never touches a plan row.
- **The human is never trapped.** The waiting screen carries "stop waiting, use the standard plan" from the first render, not after a timeout; a pack uploaded but never analysed blocks the next step with a validation naming both ways out; a user who deliberately chooses the standard plan is not caught by the same rule.
- **Outcomes are worded apart.** For the verbatim check: *found* ("5 quotes found verbatim in the uploaded pack"); *not found* (the document was read and the sentence is not in it — the agent quoted something the document does not say); *could not check* (no readable text reached the check — "this is not a finding against the proposal; nothing has been shown to be wrong with it", but still a failure, because an unverifiable quote is inadmissible). When the document reads cleanly and not one quote is in it, the message points at the likelier cause rather than concluding: the agent probably could not read the documents it was given.
- **Unverifiable means inadmissible, with the blame placed correctly.** The first version of the verbatim check passed when no document text was supplied and said "NOT VERIFIED" in its detail — a deliberate hole with a floodlight on it, because a missing input is a caller error, not an agent error. That hole was later closed when it was shown to let a proposal quote a staged document into a different client's plan while sixteen checks passed: a proposal that returns quotes when no readable text was uploaded now fails. The message still does not accuse the agent.
- **On the day, the same screen can run on a recorded proposal** through the same seam and the same gauntlet, so a rejected live proposal cannot end the demo. See `reference/patterns.md` §11.

## Why deterministic code and not a second model pass

- **The checks are literal, and literal is the point.** Set equality for completeness, membership for the whitelist, substring for quotes and for numbers-in-sentences, equality against a named library row, arithmetic for totals and dates. An agent that cites the right sentence and writes the wrong number fails on arithmetic rather than on anyone's judgement, which is the only kind of check a deterministic gate is entitled to make. A second model reviewing the first would be another untrusted proposal about a proposal, and it would need its own gauntlet.
- **The gauntlet verifies quotes and never inferences.** It binds what the agent says to the document, the library, and the agent's own figures. It does not judge whether a decision was wise; that is the human's job on the review screen, and the diff is built to make that judgement possible.
- **The whitelist cannot be weakened from outside.** The gauntlet fetches the library itself. A caller that supplies the reference set can supply a permissive one; a rule that queries it cannot be handed a lie.
- **It closes failure modes by construction, not by instruction.** Instructing the agent to quote whole sentences did not stop it shortening one; reading the document did. Instructing it never to invent ids is still in the instructions, and the whitelist is what enforces it.
- **A check that cannot fail is worse than no check, and every check is proven with an input that must fail.** Two silent skips were caught only because the harness carried deliberately failing inputs alongside the passing ones. The schedule check first parsed dates by splitting text and guarded on string length, but the JSON parser had already coerced the ISO strings into typed dates that render as nine characters, so every wave failed the guard, the check compared nothing, and its detail line read "every wave's parallel starts at least 30 days after the previous wave goes live" — a green light for work never done. Separately, `count()` returns 1 on a list of dictionaries, so the same check skipped itself on "fewer than two waves" for every multi-wave plan it was ever given; it was found by a probe that printed the wave numbers beside the count: `[1, 2, 3]` and `1`. A negative-only or positive-only harness would have shipped both.
- **Aggregate reconciliation is not enough.** The wave-total incident is the general case: parts each wrong, sum right. Recompute per item from its own source rows.

## What is deliberately not checked, and why it is written into the rule

- **A client-specific constraint stated in prose** — a blackout month during which no wave may go live — stays an instruction to the agent. A rule hard-coding that month would be wrong for the next client and silent for one whose blackout falls elsewhere. The boundary is written into the gauntlet's header and the agent is told plainly that nobody but it checks the blackout.
- **A parameter the documents state and the agent never mentions** is invisible to a rule that only sees the proposal; an absent parameter is indistinguishable from one that was never warranted. That half is held by the instructions ("a figure you read and did not act on is an omission, not a judgement") and by acceptance (the expected number of parameter changes). A gate that implied more coverage than it has would be its own kind of defect, so the rule's header says what it cannot see.
- **A requirement the library cannot meet** is the honest-failure beat made structural: the agent must flag it and hand it to a human (check 13), and a button on the review screen routes a request to the library's maintainer. It creates no plan content, changes no library row, and adds no task to the case. Inventing a task would break the single governance guarantee the architecture makes; nominating the nearest existing task is how a requirement gets quietly dropped while looking covered.
