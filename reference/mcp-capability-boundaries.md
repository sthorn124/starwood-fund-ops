# Dev MCP capability boundaries

What the Appian Dev MCP cannot do, measured across two complete builds, with the evidence shape and the workaround used. Entries carrying a **26.6.90** note were re-checked against the current server generation (`toolchain.md` §1 pin) by reading its source, diffing its tool inventory against the previous generation (145 tools → 157: twelve added, none removed), or a read-only live call; entries without one describe plugin or platform behaviour that a server update does not change, measured on the previous generation. Boundaries marked **(re-verify per instance)** depended on instance configuration or version and should be probed before being relied on; everything else reproduced or is a documented property of the surface. The standing rule from the supplemental applies: a negative claim names its evidence ("tried here, failed, here is the error"), never "the docs do not mention it". §10 records what the separately shipped sail CLI reaches beyond these boundaries on published pages, as measured in one evaluation. Its bracketed S-numbers cite that evaluation's measurement record in `examples/persona-verification-walkthrough.md`. The Dev MCP's own boundaries in §1–8 are unchanged by it.

**Tool count.** The live server reports 157 tools in `tools/list`, the same set as the 157 `@mcp.tool`-decorated functions in its source. Every tool is registered unconditionally: none is gated by tool mode, platform, plugin version, or conditional registration.

An earlier count of 148 → 160 was an artifact of the counting pipeline:
- It extracted tool names with `sed -E 's/^\s+async def …/'`, but macOS's BSD `sed` has no `\s`, so no line was reduced to a name.
- The filter that drops private helpers (`grep -v "^_"`) therefore never matched anything.
- As a result, three helper coroutines (`_list` and `_list_beta` in `objects.py`, `_wire_relationships` in `record_types.py`) were counted as tools, in both generations.

## 1. Documents and binaries

- **No binary uploads.** `uploadDocument` and `replaceDocumentContent` take content as a string that round-trips through UTF-8; every byte above `0x7F` is doubled (a 32-byte file stored as 64 bytes), so GIF, PNG, XLSX, PDF with binary streams, and ZIP arrive corrupt with no error. Pure-ASCII files (CSV, text, ASCII SVG) upload fine. Workaround: add binaries by hand in Designer, then confirm intact by reading `document(id, "size")` against the local file before wiring anything to them; prefer CSV and text formats for anything the MCP must create. **26.6.90: unchanged** — `tools/documents.py` still base64-encodes `content.encode()`, a string.
- **A zero-byte document is not creatable** — empty content is rejected, so seed files need real bytes.
- **`updateDocument` changes name and description only**; an extension cannot be corrected. A replacement template is uploaded as a new version of the existing document (Designer) so constants keep pointing at it.
- **`getDocumentText` and `getDocumentContent` return HTTP 501** (re-verify per instance). A generated document's contents are browser-only; the smart service's error message and the file's byte size are the only oracles from a session.
- **Document numeric ids are not obtainable directly** — upload, get, list, and folder-contents tools return only the UUID, and the Document record type refuses direct queries. Workaround: a throwaway multiple-valued Document constant and a rule returning `tointeger(fv!item) & "|" & document(fv!item, "name")`.
- **`document()` cannot be evaluated in `validateExpression`** (null authorization interceptor). Resolve document metadata at runtime or through a scratch process model.
- **Expression rules cannot be saved with a bare `getpdftext()`, `readtextfromfile()`, or `folder()` call** — rule validation runs with no content service — and **`a!callLanguageModel` cannot evaluate in rule context**. Take the document as a guarded input and verify through an interface; probes of this class are throwaway interfaces.
- **Design-time evaluation is capped at five seconds**; model calls exceed it. `testInterface` tolerates longer and is the only legal home for a real model call.

## 2. Record types, fields, and data

- **Column ALTER is not available.** `updateRecordTypeField(length:, updateTable: true)` returns 200 and changes nothing physical; the only way to widen a column is `deleteRecordTypeField` then `addRecordTypeField` (new UUID, every row nulled including invisible ones, every reference repointed by UUID and re-rendered), or Designer. `createRecordType` ignores nested `fields[].length`; add long fields separately.
- **Mapping an already-existing external column onto a record type is a Designer re-sync**, not an MCP operation: `addRecordTypeField` with `updateTable: false` returns `HTTP 400 Non-CDM field operations are not yet supported`, and `updateTable: true` would alter the external table. A record type cannot enumerate an external table's columns either.
- **Record List column configuration is not exposed**, and a record list has no per-viewer condition; generated lists default to raw foreign-key integers. Workaround: Designer, or interface pages with record-bound grids.
- **Record actions cannot be reordered** — `reorderRecordTypeViews` exists, no action equivalent does, and a view's `relatedActionShortcuts` ignores the order sent. Designer reorders; `listRecordTypeActions` confirms.
- **Field-level security (`a!doesUserHaveAccess`) is Designer-only**; over MCP a masked display is a visibility demonstration, not a boundary. Field auto-population settings (created-on and the like) are Designer-side too; the write path must populate them.
- **Delete constraints do not exist and CDM tables carry no foreign keys**; referential protection is enforced in the form and stated as form-level only.
- **Objects outside an application are effectively unfindable** — nothing lists them, there is no lookup by name, and `getExpressionRule` returns the same 403 for "does not exist" and "is not a rule"; an id-space scan is not a search. Designer searches by name in seconds.
- **`getObjectDependents` is the only reverse index.** It returns object-level breadcrumbs (no field names), rejects a record-field UUID, and lists the application as a member rather than a consumer. A field-level census is: dependents list → fetch each source → grep the field UUID.
- **Existence checks return different shapes per type** — a deleted process model answers HTTP 500 "Does not exist", a deleted interface 404, a missing rule 403. Prove presence first, then treat any non-200 from a targeted get as absence.
- **The data-fabric SQL tool is read-only SELECT, runs under a different identity, and its metadata index does not enumerate external-backed tables**; treat a zero-row answer from it as blind, never as evidence of absence.
- **`a!deleteRecords` inside a `saveInto` cannot be exercised from a session.** The delete is performed through the record-data API on seeded throwaway rows to prove the cascade, and the click itself is handed to a human.

## 3. Record events and audit

- **Record events are generated through `configureRecordEvents`, not through Designer's generator wizard, and the wizard's extras are Designer-only.** The generator does not copy record-level security onto the Event History type despite its own description (add the RELATED_RECORDS rule by hand and read it back); a custom field added to Event History in Designer never appears in the Write Records node schema over MCP (sending it fails HTTP 400 "use customInputs"), so `comment` is the only per-event detail field and only where commenting is disabled app-wide; the generated types have no views; `generateCommonEvents: false` yields only custom types plus unused reply-thread and subscriber types.
- **Only the Write Records node writes events**; `a!writeRecords` in a `saveInto` cannot, and the node's event parameters appear only when its schema is fetched with the base record type as `referenceUuid`. The node's input list is fixed.
- **`AutomationType` renders nowhere on its own**; a distinction a reader must see needs two event types.

## 4. Process models

- **No process instance surface.** Instances cannot be enumerated, a paused instance's variables cannot be read, and an instance cannot be cancelled or resumed; `appian_get_process_status` on the runtime server needs an id already in hand. Stranded instances are handled in Process Monitoring by hand, and an instance keeps running on the model version it started with (cancel, do not resume). **26.6.90: unchanged** — the tool inventory adds no instance tools.
- **No recurrence; multiple node instances now exposed.** `core.0` exposes no inputs and `updateProcessModel` has no recurrence field (`event.timer` is a delay), so a scheduled model is built complete over MCP and its recurrence set on the start event in Designer — **26.6.90: still true**, no recurrence field anywhere in the process-model tools. Multiple Node Instances were absent from the previous generation, which forced a per-item fan-out to be an explicit loop (index PV, seed, XOR against the count with a hard ceiling, work nodes, increment, flow back); **26.6.90 adds a `multipleInstance` block** on `createProcessModelNode` and `updateProcessModelNode` (`instances`: FIXED_COUNT, PROCESS_VARIABLE_VALUE, PROCESS_VARIABLE_ITEM_COUNT, or ASSIGNEE_COUNT for attended nodes; `parallel`), a full replacement on update, plus `clearMultipleInstance` to turn it off. Its runtime behaviour has not yet been measured in a build; the explicit loop remains the proven pattern until it is.
- **No Exceptions tab** in the node payload or `updateProcessModelNode`, and fail-forward is a per-smart-service node input with a different name each time (`Pause On Error`, `Pause Node on Error`, `Pause Node on HTTP Error`). A service that offers none has no fail-forward mode at all; the only remedy is not to run it in the main flow.
- **`errorAlertGroupName` is not settable** — accepted on create without persisting, rejected on update; set in Designer. **26.6.95:** `createProcessModel` no longer takes `errorAlertGroupName`; it takes `errorAlertGroupUuid` (the tool suggests `getApplication` → `defaultObjects.administratorsGroupUuid`). Whether a UUID now persists is **not yet measured**, so keep the Designer step and a readback as the known-good path until a create proves it. **"Run multiple instances" and the Move Document node's single `Document` input** are unreachable; a loop-back edge handles N.
- **`updateProcessModel` is a full replacement** of nodes and of the process-variable list; a partial array is rejected; a failed update rolls back everything in the call; a PV cannot be removed while a node references it (HTTP 500 — add, repoint, then drop); a new model's default End node (id 2) can neither be reused nor deleted, so new nodes are numbered around it. `createProcessModelNode` is not an upsert, and a node's `data` is a full replacement on update.
- **The subprocess node schema exposes only parameter PVs as outputs**; locate a written row by query (natural key plus session tag plus status) rather than by output mapping. PV default expressions cannot reference other PVs.
- **`testProcessModel` parameter type limits** (measured on the previous generation; **26.6.90 changes the contract**, see the end of this entry). It cannot pass a Date (arrives as an integer; `todate()` does not rescue it), a Date and Time (marshals to an epoch-overflow value and fails loudly at the write), a Document or Document list (arrives null), a real temporary upload, a record-typed value, or an Any Type record list: a string is quoted and never evaluated (`Received: Text`); a nested object with UUID-qualified keys breaks map construction (`Invalid operator 'open_brace'`); a nested object with plain keys marshals to a Map (`Received: Map`), so the process starts, runs every upstream node on a value it could not read, and fails at the write — a degraded-but-plausible upstream result, and a garbage row if any upstream node writes. Workarounds, in order: exercise the branch that skips the write; give the PV a default expression and omit the parameter; set timestamps afterwards with `updateRecordData` (CSV, `YYYY-MM-DD HH:MM:SS`, UTC); a throwaway harness model that computes the payload in a node (`customOutputs`) and calls the real model as a synchronous subprocess; mirror post-write compositions in a throwaway rule; hand the end-to-end run to a browser checklist, or, where a persona reaches the model's start form through a site, drive it through sail (§10); and say which was done. **26.6.90:** the tool's own description now states inputs are literals and that temporal values use `yyyy-MM-dd` (Date), `yyyy-MM-dd HH:mm:ss` (Date and Time — the ISO `T` form is rejected), and `HH:mm:ss` (Time), so the Date and Date-and-Time limits above were measured with the ISO form and need re-measuring with the documented formats before being relied on; the record-typed and Any Type limits are unchanged in principle (literals only) and likewise unmeasured on this generation.
- **No models with user input tasks or Any Type parameters.** `testProcessModel` refuses any model containing an attended node (mid-flow or terminal), and the refusal arrives as a bare `Network error:` rather than a message; the runtime invoke tool returns HTTP 500 for the same model and separately rejects any model with an Any Type parameter (`Unsupported tool input type(s): Variant`). Keep verified paths unattended; put forms on the process start (`testProcessModel` skips a start form and maps inputs onto parameters, so scalar-parameter related-action models are exercisable end to end). Nothing over MCP can advance a process or fire a poll transition. **26.6.90 narrows this:** `testProcessModel` still states it works only for unattended models, but `listMyTasks` and `completeTask(taskId, inputs)` now exist, so an attended task assigned to the running account can be listed and completed over MCP — listing verified live (the design account's queue came back), completion not yet exercised. Outside the Dev MCP, sail drives a start form a persona reaches through a site, and submitting it starts the process (§10).
- **Process branches requiring a role the MCP identity lacks are unreachable**; compose the branch's output with a throwaway rule fed real values. **Email delivery is not observable** over MCP.

## 5. Interfaces and rendering

- **No clicks, no typing, no state.** `testInterface` returns a component tree of the initial render: it cannot press a button, open a dropdown, operate a type-ahead picker, drive `a!fileUploadField`, toggle a section, or complete a wizard step. Workarounds: flip defaults in a probe copy and restore (verified byte-identical); throwaway rules for gate truth tables; the browser for the click. On a published page, sail clicks, types, and submits as a persona (§10).
- **No impersonation.** `testInterface`, `testRule`, and `testProcessModel` evaluate as the calling account, so only that account's branch of any viewer-conditional surface ever renders, and the design account is usually full-scope. Workarounds: byte-copy shims with counted substitutions (`loggedInUser()` → `touser("x")`, or the membership rule swapped for a mirror taking `ri!isMember`), named `zz`, deleted and confirmed absent afterwards; persona clicks by a human. On a published page, a sail session logged in as the persona itself replaces both (§10).
- **The render tree carries no geometry** — no pixel widths, line breaks, wrapping, truncation, overflow, hover, focus, link colour, scroll, chart type (bar and column charts serialise identically), or height (named enums with no pixel values). Everything geometric is a browser check; the deployed expression readback is the evidence for choices the tree cannot show.
- **Not serialised in the tree and therefore unverifiable from a session:** grid `searchFields`, chat `instructions`, export content, whether a record view refreshes after a related-action dialog closes, and whether a timer fires.
- **Record-header renders are unreachable.** `titleExpression` and `relatedActionShortcuts` are settable, but the rendered title string and the header action set render outside any interface; a status-driven action set configured on the header has no automated verification from the Dev MCP. sail lists a record view's actions per persona (§10); a status-driven change in that set has not been measured.
- **`a!wizardLayout` renders only the active step**, cannot be advanced, and its step properties (`disableNextButton`, `validations`) are invisible to both render routes.
- **The vendor pack's component references are incomplete and wrong in places** (a missing `a!kpiField` entry, `labelPosition` examples carried across components, a grid-binding rule that does not hold); probe with a throwaway object and record corrections in the supplemental, never by editing the pack.
- **Browser automation from a session lands on the site's SSO**, connected-browser listing returns empty, and credentials are never entered; screenshots are supplied by a human. Persona sessions for content and behaviour come from sail logins the operator performs (§10).

## 6. Sites and security

- **Site branding is preset-only** — six fields, `style` in MERCURY / HELIUM / OXYGEN; hex branding and CSS profiles are Admin Console, site-level, with no per-component reach and no focus state.
- **Site page width and accent colour are not exposed**; a `width` key is accepted with 200 and dropped; `getSite` returns per page only uuid, name, web-address identifier, target, type, description, icon, and visibility expression. Full-width pages are a Designer setting (re-verify per instance).
- **Page types are INTERFACE, RECORD_LIST, and ACTION only; no page groups or nesting** (groups take interface pages only anyway); top-level items are capped (stated ceiling eight). `updateSite` can set page visibility expressions (measured), and any `updateSite` regenerates every page UUID and URL stub.
- **Group membership: reading now works, writing unverified.** On the previous generation `createGroup` succeeded and the group listed, but the name-addressed `addGroupMembers`, `getGroup`, and `listGroupMembers` returned HTTP 403 "Group not found or access denied", including against long-existing groups the same account listed — so a group created over MCP stayed empty and a site gated on it was invisible to everyone until a human added the first member in Designer or the Admin Console. **26.6.90:** the group tools are UUID-addressed, and reading works — `listGroups(appUuid)`, `getGroup(uuid)`, and `listGroupMembers(uuid, directOnly, memberType)` returned a group and its members on a live read-only call (user display names still come back empty; `directOnly` separates explicit from inherited membership). `addGroupMembers(uuid, members)` and `removeGroupMember` exist but were not exercised; treat membership writes as unverified on this generation and the Designer step as the known-good path until one is measured. `deleteGroup` is also UUID-addressed now.
- **Cross-application object security cannot be granted** — `updateObjectSecurity` on another application's document returns HTTP 500 "Name is insufficiently unique" for any group. Re-home the asset into the consuming application's folder.
- **`getObjectSecurity` reports administrator, editor, and viewer only** for process models — no Initiator role — and distinguishes direct from inherited grants, which is the only way to see that a folder grant covers every inheriting object.

## 7. Agents (platform and MCP)

- **Agents are read-only over the Dev MCP.** Four get/list tools, no create, no update; Agent Studio is the only creation path. Design artifacts are authored as files (`agent/instructions.md`, `tools.md`, `eval.md`), the agent is built by hand in Agent Studio from them, and verification is behavioural through `testProcessModel` with row counts and the structured output map.
- **Agent Studio instruction text cannot be read.** `getAgent` errors (`Unexpected error: 'type'`, with and without `expand`) on the instances measured; `getObjectDependents` on a tool rule returns the agent as an `AI_AGENT` dependent with its UUID — the binding, never the instructions or the declared input and output names. Wiring an agent node is therefore a hand-off: the input names come from whoever built the agent, and a session stops rather than guessing spellings. **26.6.90: persists** — on a live read both `getAgent` (with `expand`) and `listAgents` fail with the same `'type'` error on the measured site, and the agent tool module is byte-identical between generations, so the fault is on the response side, not in the server. (both builds)
- **Agent tool calls are not observable from a process run**; `RunSummary` is not a trace and fabricates. Tool-economy evaluation needs Agent Studio's monitor view and is a human's to run.
- **Record-type agent tools return only the record type's own fields, with no relationship traversal**; the Record Fields panel on the tool is display-only, not a picker. Related context costs one tool per record type per run or process-side assembly into a single text input — prefer the latter.
- **Agents query one record type at a time**; joins and aggregations are expression-rule tools. **Agent folder tools surface prose only** — a CSV is invisible to semantic search and document read; structured files are parsed by a deterministic rule tool.
- **The Execute AI Agent node is a smart service**: it cannot be called from an expression rule, there is no supported route to read process variables from an interface, and a synchronous `a!startProcess` is capped at 30 seconds while an agent takes 40–60. Workaround: start the process, write a run row, poll with `a!refreshVariable`.
- **The agent's execution identity is not visible from a session**; tools take the requesting user and fail closed, and the process-side context assembly runs under the process initiator's scope.

## 8. Session and environment

- **The design-object tool surface can be transiently absent** ("No matching deferred tools found" for every CRUD tool) while `ping` returns 200 and `claude mcp list` reports connected. It returned on its own the next session; treat it as retry-next-session and stop the build half rather than substituting runtime tools. A runtime server registered under the same name produces the same symptom, since its own `ping` answers, and it does not clear on retry. When the tools present are the runtime family, fix the name instead (`toolchain.md` §2) [S34]. **26.6.90:** `getDevMcpVersionInfo` reports both halves' build stamps and whether they drifted apart; run it first, so a version-drift or wedged-server problem is not debugged as a tool bug.
- **The session's permission classifier can deny a tool call** (a no-write `testProcessModel` was refused); this is session configuration, not platform behaviour, and is reported rather than worked around.
- **No execution path to an external warehouse or console from a session.** DDL, procedures, and verification queries are delivered as scripts a human runs, statically checked (tokenised with comments and strings stripped, parentheses balanced, forbidden tokens absent, expected counts of bodies and checks), with unresolved values left as deliberately invalid markers so nothing deploys silently.
- **The docs-search MCP expires** and drops out of a session; the in-app browser cannot log in as a persona (sail can, from the operator's login; §10).

## 9. Things that do work, contrary to expectation

Recorded because a build assumed otherwise and lost time: `configureRecordEvents` generates events with no Designer step; `addRecordTypeView`, `reorderRecordTypeViews`, and `deleteRecordTypeView` work (a new view appends last); `updateSite` sets page visibility expressions; the Execute AI Agent node (`internal3.execute_ai_agent`) is fully configurable over MCP (`AgentUuid`, `AgentInputs` map, `Async`, outputs to PVs); Send E-Mail (`internal3.sendemail3`) is available with the four traps in the supplemental; `getProcessModelNodeTypeSchema` with `referenceUuid` exposes a child model's parameters as named inputs and outputs; `updateRecordTypeAction` has partial-update semantics; `deleteProcessModel` and `deleteInterface` return "Deleted successfully"; `testProcessModel` runs a model that has a start form; `getObjectSecurity` reveals inherited viewer groups; query traversal works across data-source handles; an optional input can be added to a shared interface rule without touching its callers; a raw Unicode glyph in an expression payload round-trips the transport intact (the doubling is specific to `uploadDocument`).

**Added in DevMCP 26.6.90** (verified from the tool inventory and source; runtime behaviour measured only where stated): `getDevMcpVersionInfo` reports the plugin's and the bundle's versions and build stamps and says whether they drifted; `logout` deletes the persisted session and browser profile; every `get*` design-object tool takes a `version` parameter to retrieve a past version, and `listObjectVersions` lists an object's version history — the answer to "which versions were probes" in `toolchain.md` §7; `listMyTasks` and `completeTask` (listing measured live); `multipleInstance` on process-model nodes; a portal tool family (`createPortal`, `getPortal`, `listPortals`, `updatePortal`, `deletePortal`, `publishPortal`, `unpublishPortal`); `getGroup`, `listGroupMembers`, and `deleteGroup` addressed by UUID (reads measured live); and pre-submission expression fixups that auto-quote record type references whose names contain spaces and reject record type references without UUIDs before they reach the parser, so a class of misleading lex errors no longer occurs.

**Changed in DevMCP 26.6.95.** Verified from a source diff against 26.6.90 on 2026-09-21. Formatting-only changes were separated from logic changes by comparing ASTs. No runtime behaviour below was measured unless stated.

- **Unchanged:**
  - The tool inventory: 157 `@mcp.tool` functions, the same names in both generations, equal to the session's live count.
  - `browser_auth.py`, which is byte-identical.
  - The environment variables read.
  - `groups.py`, which changed only by reformatting. Group reads were re-measured live on 26.6.95: `listGroupMembers(uuid, directOnly: true)` returned three direct members.
- **Inline-SAIL guard on `createInterface` / `updateInterface`.**
  - When the server runs with `SAIL_MCP_ENABLED=true` ("pipeline mode"), an inline `expression` is rejected with a structured error. The error directs the caller to create the interface without an expression and then call `generate_interface_sail`.
  - `generate_interface_sail` is not in this server's 157-tool surface; it belongs to the sail-mcp pipeline.
  - The documented registration (`toolchain.md` §1) sets only `LCP_URL`, so the guard is **off** and inline SAIL writes behave as before.
  - If a registration ever adds `SAIL_MCP_ENABLED=true`, inline interface writes stop working over this server.
- **`createProcessModel` takes `errorAlertGroupUuid`** in place of `errorAlertGroupName` (§4 entry above). Persistence is unmeasured.
- **Record type `securityMode` is validated client-side.** Only the two API values are accepted. The internal name `GUIDED` is rejected with the plugin's own wording, rather than surfacing as an "Unexpected error".
- **Integrations can save a response as a document.**
  - With `responseBodyParsing` `CONVERT_BINARY`, or `CONVERT_JSON` with `convertBase64ToDocument`, the folder and the name each take one of a mutually exclusive pair: a literal or an expression.
  - `CONVERT_JSON` also takes up to five distinct `documentLocations`.
  - Designer's location picker looks empty until Test Request is clicked, but the stored locations work, per the tool description. This is unmeasured.
- **Delete responses.** Every 2xx on a DELETE is now treated as success; previously a 204's empty body could be misread as an error. A delete is still proven by absence (`CLAUDE.md` §4), never by the response.
- **Write checkpoints.** Before an update or delete tool runs, the server tries to snapshot the target through a design-object checkpoint API, and it records version pairs after the write.
  - These are for a hosted copilot's rollback: they need a callback URL and a site that supports checkpoint API version 2026-07-17 or later.
  - Failures are swallowed and never block the write.
  - Nothing of this surfaces in a local stdio session. Do not treat it as a rollback mechanism here: `listObjectVersions` plus `get*(version)` remain the way to recover a prior version.

## 10. Beyond the Dev MCP: what the sail CLI reaches

sail is a separate tool with its own identity (`CLAUDE.md` §6), not a Dev MCP capability, and nothing in §1–8 changes for the Dev MCP itself. What it changes is what a session can verify, as a persona, on published pages. Everything here was measured in one evaluation (`examples/persona-verification-walkthrough.md`, S-numbers) except entries marked *per sail's help*, which were not exercised. The tool's surface is in `toolchain.md` §12.

- **Persona sessions, not impersonation.** A session drives pages as the persona's own local account, logged in once by the operator. Every page, value, and action then renders under that persona's security [S4, S32]. SSO-only identities cannot password-login, so they cannot be persona-verified this way (*per sail's help*). The one SSO path, `--from-devmcp`, imports the designer (`CLAUDE.md` §6). Narrows §5 *No impersonation* for published pages.
- **Clicks, typing, and state on published pages.** The following were driven, each cascade read from the returned diff (a dependent button enabling, a form restructuring, rows swapping) [S10, S11, S15, S16, S18, S22]:
  - record links, tabs, related actions, and disclosure links;
  - dropdowns, text and date fields, and picker search;
  - grid sort, grid search, and filters.

  Narrows §5 *No clicks, no typing, no state*. An interface not placed on a page is still reachable only through `testInterface`.
- **Start forms and process launches are drivable.** Three related-action start forms were driven and two submitted; each submit returned a process id, and fresh reads confirmed the writes [S11, S13, S19]. A site-level process launch opened its start form, took dates, and ran its validation [S21]. Narrows §4 *No models with user input tasks*, and *nothing over MCP can advance a process*, for forms a persona reaches through a site. User input tasks reached from a task list were not measured: the persona's account had no task page.
- **A record view's action set is readable per persona.** The related actions a record view offers are listed for the account that reads it: 29 for the design account and 26 for a persona on the same record [S32]. Narrows §5 *Record-header renders are unreachable* for the action set. A status-driven change in that set, and the rendered title string, were not measured.
- **Validation and confirmation are observable.** Required-field and format validations come back as ⚠ lines and `[INVALID]` field state, and the form stays open [S12, S21]. A button the browser would confirm first carries a `confirm:` line and is refused until `--confirm` [S19].
- **Row-scoped actions that share one label are not drivable.** An action rendered once per grid row under one label was refused as naming 43 destinations that "cannot be told apart", and the stored UI carries no row-qualified handle [S9]. Drive the row's own record view instead, or hand the step to the browser.
- **Document downloads are not reachable.** Five download links on a record tab were refused by `navigate` and by `interact` [S9]. Document access as a persona stays a browser check.
- **Plain URL links are not followable** — *per sail's help*, `<url>` is "a plain hyperlink no sail command can follow". No such link existed on the measured pages [S9].
- **Chart values and paging were not measured.** *Per sail's help*, a chart's plotted values appear as `<display>` text, and a chart's points and a grid's pages are `handle:` targets. No page the persona reached had a chart or a grid past one page [S9].
- **No geometry.** The stored UI carries style values and requested layout parameters, and nothing computed [S8]. §5 *The render tree carries no geometry* holds for sail too.
- **No identity query.** No command prints the acting account, and the session file records only the name typed at login [S2, S25]. Every sail observation states its account.
