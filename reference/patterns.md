# Working patterns

Reusable patterns from two complete Appian Dev MCP builds and one measured evaluation of the sail CLI, stated generically. Each names the mechanism, the reason it exists, and the failure it was bought with. Where a pattern rests on a measured platform fact, the fact lives in the supplemental skill and is only pointed at here. Bracketed S-numbers cite the sail evaluation's measurement record in `examples/persona-verification-walkthrough.md`.

## 1. Prompt-driven specs

- **Detailed build specs live in collaboratively written build prompts.** A build pass is specified in a prompt developed in the session with the owner — requirements, acceptance, the objects it may touch, the rulings already made — and the prompt is what the session executes against. Prompts are not fired as mega-prompts; they are worked up in conversation and then run.
- **`BUILD_PLAN.md` stays a high-level checklist.** Phases and tasks, `- [ ]` becoming `- ✅ <date>` at close-out, newly discovered tasks added to the right phase. It is the state of record for what is done and what remains, never the place where a feature is designed.
- **Recon before build.** A no-build recon session answers the questions a build prompt must settle — what exists, what the platform allows, which of two designs is cheaper and why — and ends with an explicit "open decisions a build prompt must settle" list. Recon is logged in the build log retrospectively rather than left to survive only in a prompt.
- **The prompt is corrected against the environment at preflight.** "After X" and "the existing Y" resolve against what actually exists in the environment, not against what the prompt assumed; the deviation is disclosed in the entry.
- **Claude Code build prompts are saved as files.** `prompts/NNN-<slug>.md` — a three-digit sequence in run order, one file per prompt, the prompt exactly as pasted (`GETTING_STARTED.md` §4) — so the specification of every build pass is in the repo and diffable, and `BUILD_PLAN.md` points at prompts rather than restating them.
- **Every word a model inside the application is given lives in a file.** `prompts/model/<name>.md` is the source of record for each model prompt: reviewable ("what did you tell it to do" is answered by opening a file), versioned (a prompt change is a diff), portable across the agent seam (the same text is pasted into Agent Studio and concatenated for any expression fallback). A script mirrors each file into a trivial expression rule that returns the text (under `prompts/model/_generated/`), writes a checksum beside it, and has a `--check` mode that fails when the deployed mirror is stale.
- **Prompt rules that held across both builds:** ask for JSON and nothing else, then enforce the schema by a deterministic parse that rejects and retries; never let the model invent an identifier — every returned id is whitelist-checked by the caller; state in the prompt what to emit when the input does not contain the answer; expect a prose preamble before the JSON regardless of instruction and strip everything before the first brace.
- **Agent instructions are replaced wholesale**, never patched in place, and the file records the version history with what each change was for and which measured failure it closed.

## 2. Mockup-driven UI

- **HTML mockups are iterated in chat and banked in `mockups/`**, one per interface, before any SAIL is written. They are the guide for build passes and the structural authority for a screen's information hierarchy and display vocabulary. Mockups stay local to each build; none belong in this template.
- **Mockups are aspirational; build to the nearest platform equivalent.** Information hierarchy over pixel styling. The platform deltas that are never fought (no per-interface fonts, no segmented progress component, no expandable or grouped grid rows, no sticky footers, no custom hover, no brand bar inside an interface) are in the supplemental; each build's own translations are a component-mapping table in its `CLAUDE.md`.
- **Mockup deltas are tabulated with reasons** in the build log for every screen — each figure or element that could not be built, and why — and a **structural delta is a delta too**: when the built layout departs from the mockup by ruling, the log says so and the mockup is fixed in the next mockup pass, or the next session "restores" the shape that was deliberately changed.
- **The mockup's CSS is the type authority.** Map the mockup's sizes to the nearest platform size; never invent a scale. Emphasis is weight and colour, never a third size.
- **A display label not evidenced by a mockup is declared, not coined.** Where the mockup shows no label for a state, the canon says so explicitly and the owner ratifies one; stored values never change for display reasons, and every enum that reaches a screen goes through a named display rule rather than a casing trick.
- **Provenance marks intelligence, not residence**, when a screen must show where a value came from: mark the values a model or an external system computed, never values that merely live there, and render the mark from one object so it cannot drift.
- **Verification against the mockup splits by kind** (`CLAUDE.md` §4):
  - **Through sail, per persona (§12):** the content, display vocabulary, field states, and behaviour a mockup specifies. Tag values and full grids are read from the stored YAML [S7].
  - **In the browser, against the mockup:** geometry — layout, wrapping, card heights, colour as painted — because sail's stored UI carries no computed layout [S8].

## 3. The `agent/` folder pattern

Worked example: `examples/agent-eval-walkthrough.md`.

The Dev MCP cannot create or edit agents (see `mcp-capability-boundaries.md`), and on some instances it cannot even read one, so agent design is done as files and the agent is built by hand.

- **`agent/instructions.md`** — the verbatim instruction block currently deployed, marked as such, followed by commentary for the maintainer: version history with the measured failure each version closed, why particular clauses are as blunt as they are, which rules are enforced structurally elsewhere (a category that must always go to a human is tested by the process directly and never trusted to the agent), and the input contract (name and casing of every input — load-bearing, because a mismatched key is silently ignored and the declared names cannot be read over MCP).
- **`agent/tools.md`** — one section per tool: type (expression rule, record data, MCP), backing object, input, output shape, grants the agent identity needs, scope discipline. Tools deliberately NOT built get a section too, with the reason (a write tool would create a second write path to the same fields and let a write precede the gate that decides it).
- **`agent/eval.md`** — the evaluation suite: seed cases per tool with expected outputs; the held-constant specimens (a clean case, a concerning case, an authored hero) with every fact listed; a results table per instruction version showing each specimen's output and lane; the pass condition stated as content the output must contain (the arithmetic stated number against number), never as a score that could be reached by luck; contract-conformance checks (all keys present, tool outputs byte-identical, confidence not a copy of an upstream score, tool-error path reported with confidence zero); and the running record of any output field found to fabricate.
- **The human builds the agent in Agent Studio from these files.** Until it is wired, the process model carries a placeholder node whose description says what replaces it. Wiring an agent node is a hand-off point: the session cannot verify the input names, so it stops and asks rather than trying spellings.
- **Verification is behavioural.** Runs are driven through `testProcessModel` as the design account; outputs are read from the structured output map and from rows written per record type, never from the run summary field; tool calls are not observable from a process run and are checked in Agent Studio's trace view by the human.
- **The eval log tracks instruction versions against held-constant specimens.** Every instruction change is probed in both directions on the same specimen pair; a single wrong-side reading is replicated before it is called a regression (it has been measured as variance straddling a threshold); when two changes ship together, attribution is recorded as unresolved.
- **Design rules learned the expensive way:** assemble the agent's context process-side into one labelled text input (record tools do not traverse relationships, and process-side assembly runs under the process's security context); give one context input, not four tools; write the one-call prohibition explicitly (tool-description economy does not stop corroboration calls); treat output descriptions as prompt surface; exclude upstream model scores from the agent's own confidence by name; require numeric tests to be stated arithmetically; enumerate concerning facts as a closed list; bind documents to inputs rather than folder tools, so the agent cannot reach a document the run was not given; share one extraction rule between the agent and the checker so both read the same characters.

## 4. Authored demo packets

- **Reserved id ranges.** Demo-authored rows carry an id shape no organic row can carry (a prefix the baseline never uses, then a run code, then a sequence), so collision is impossible by construction and a reset can name its rows exactly. Baseline readiness counts exclude the reserved range so a loaded packet never reads as corruption.
- **INSERT-only seeded specimens for demo beats the organic data cannot produce.** When no organic row has the combination a beat needs (favourable facts at high risk; a genuine cascade; a case in every status), the specimen is authored rather than adopted, under a per-build packet spec file that is the contract for the rows, the mockups, and the talk track. Authored rows are shaped like the baseline and internally coherent (a story's factors never contradict its reason or its lane); coherence is enforced at authoring time, not discovered on stage.
- **Timestamps are relative to now at insert time**, so a simulated feed never needs re-dating; hand-authored verification fixtures, by contrast, are re-dated by script before every session (§5).
- **Reset is by exact id list**, never by prefix match with a variable-length code (`LIKE 'X' || code || '%'` deletes a neighbouring run).
- **Specimens are identified by their properties, never by platform-assigned ids**, which change on relaunch; the seed is stable and anything above it is disposable; protection is a property of the write path (explicit id lists), not of a name someone has to remember.

## 5. Demo repeatability

- **Session-tagged data.** Every row a demo run creates — cases, comments, audit events, external-system rows — carries a session or run id. Baseline data is never mutated by a run. Uniqueness constraints that are "one per entity" hold only within a session and are enforced by the create path's guard query, never by the relationship.
- **A reset action** deletes the session's rows by explicit id (children by measured cascade, never assumed), in cross-system order — the system whose rows point at the other goes first, and the second system is touched only if the first delete succeeded — refuses the fixture session by name in the UI and again in the process, and normalises the run name (upper-casing on both the load and reset buttons) so tags can never differ by casing across systems. External procedure messages are shown verbatim, OK and REFUSED alike.
- **A verify-ready action** is read-only: baseline counts excluding the reserved range, zero open demo rows, a one-row reachability probe per record type, one cheap call to any external system, and the agent's last run read from the audit trail rather than invoked (a check that writes the rows it checks is not a check). The checklist has three states — green, red, and a neutral dot for lines that report a state rather than assert one — so red stays meaningful.
- **The operator console is a separate site**, gated on a group outside the users tree; the presenter is not a persona, and a reset button one tab away from the demo screen is a wrong click from deleting the case being shown. Process-model and integration security must let that group start what the console starts, and the presenter must hold the scope the intake reads under, or row security silently finds only part of the packet.
- **Demo-morning runbook: three items and nothing else** — delete practice rows, check the live agent, confirm the fallback artifacts are open. It is a per-build `RUNBOOK.md`, not part of the template. Maintenance (calendar reshift, fixture rebuild, document replacement) lives in a separate per-build file (`MAINTENANCE.md`) and is never demo-morning work. The fallback is a product path (the deterministic route the agent's proposal is a diff against) plus saved artifacts — a completed run, a pre-generated document, screenshots for every AI beat — never a mode flip.
- **Calendar drift** is answered by a reshift model that moves every seeded date by one uniform offset derived from the data (so running it twice is harmless), scoped to an explicit id list; time-anchored fixtures are re-dated by an idempotent offset-from-now script at session start, and every table stamped on the same clock moves together or the audit trail lies.
- **Known data artifacts** that look like defects and are not get a section in `CLAUDE.md` with three parts each: what shows, why it is there, what to say in the room.

## 6. Agent decides, deterministic code disposes and verifies

Worked example: `examples/deterministic-validation-gauntlet.md`.

- **The model proposes; code validates, applies, renders, and writes.** Every agent tool is read-only; there is no process tool on the agent; the process model consumes the agent's structured output and does the writing on the branch its own routing decided. Route conditions test data directly (a category that must always go to a human is tested by the XOR, not trusted to the agent); prohibitions are encoded as data where possible (a null outcome code in the lookup makes "never auto-resolve" a property of the data).
- **A gauntlet of deterministic checks binds the proposal against the source and against itself:** ids whitelisted against the reference data, completeness asserted (exactly the expected set, no additions), arithmetic recomputed per item rather than reconciled in aggregate, quotes verified verbatim against the uploaded documents with whitespace stripped, self-consistency between the agent's own numbers. Checks fail closed: a check with nothing to verify fails rather than passing, every check has an input that must fail, and assertions are two-sided (the expected value present and the default absent).
- **The proposal is presented as a diff against the deterministic path**, each deviation with a rationale, human approval required; the agent's numbers are frozen on screen and the user's divergence sits on its own line. A rejected proposal falls back to the deterministic path with a stated reason.
- **Confirmation is a control, not a courtesy:** the counts shown after a write are read back from landed rows, and the row that records a run is opened before anything that can fail.
- **The seam is text**: the agent returns text, the fixture returns the same text through the same parse and whitelist, so a fixture run exercises the production route rather than a shorter one.

## 7. Guard patterns

- **A context-resolved gate before every agent node.** An XOR that queries whether the context the agent needs actually resolves (null-guarded, because the identifier can be null at validation), whose default path goes straight to End writing nothing. Empty or failed context kills the flow instead of feeding the agent; the model is never relied on to report its own blindness. Break-tested with an unresolvable id: completes in seconds, no agent invocation, no writes, counts unchanged.
- **Write-success gates before audit writes.** One Write Records node per record type, chained; `ErrorOccurred` and `Error` wired to process variables on every business write; an XOR reading `a!defaultValue(pv!err, false())` between the last business write and any event node, defaulting to End. Sequence is not a guard.
- **Idempotency in layers:** a guard query plus XOR before every create; a plan-level skip of anything already processed for this run in any status; downstream steps started only on rows found in the expected initial state.
- **An id guard before every event write** (a null primary key inserts a phantom row instead of logging) and **a success-flag guard before every "document generated" entry** (a failed generation never leaves an entry claiming a document exists).
- **Record the failure before the thing that can fail:** the run row that makes a failure visible is written first, and a new, untested node is never placed ahead of the node that reports.
- **Cross-system order:** the system whose rows reference the other is cleared first, and the second is touched only on the first's success.
- **Navigation visibility fails open; data checks fail closed.** A page gate that cannot resolve the user shows the page, because the security boundary is the record-level rule, not the tab.
- **Stated-retreat switches:** a constant that flips a fragile dependency (an asset owned by another application) to a fallback, whose description says it is a retreat and not a fix, with the durable fix tracked with a trigger.

## 8. Display and audit doctrine that carried over

- **A screen renders the stored decision and never re-derives one**; derived-state display rules carry their state to consumers rather than letting consumers recompute.
- **Fixture prose is composed from the row**, never authored beside it, with the same rounding the screen uses, as of the row's own run timestamp; a dated assessment disagreeing with the live clock is a correct audit artefact, not a bug to fix.
- **Audit sentences are composed at write time from values in hand and frozen**; identifying content first, trimmable content last, cap equal to the measured column; maintenance machinery never logs; coverage is defined by a write-path census (business, maintenance, pre-record).
- **Machine-authored content carries attribution** that replaces the label rather than joining it; one navigation door per excerpted record; a list that truncates says so.

## 9. Dashboards, imports, and copy

- **The coherence invariant on a dashboard is structural, not procedural:** one query, one derived row set, every KPI, chart, and grid a filtered view of that set, and any difference the screen must show reconciled in words on the screen. Verified arithmetically across every card before it ships.
- **Import contract:** preview validates before any write; nothing is staged while any row is in error; no key or order columns in the file; confirmation counts are readbacks; rows that did not land are named on the confirmation.
- **One implementation per mechanism.** A single rule for each computed presentation and each condition (a display label, a gate, a provenance marker); a fourth wording of the same number is a fourth chance to disagree with itself. A surface census is a source read of every interface and rule plus their dependents, not a grep.
- **Screen copy is for the reader, not the builder.** Define a concept once, no internal vocabulary, no build-state or phase messages on a console; verify that no internal term reaches the render. Destructive typed-id affordances are guarded by name: the protected fixture is refused, the button disabled, the refusal copy explicit, and an unknown id says so instead of deleting zero rows silently.
- **A new field must be carried by every writer**, or it exists only on today's data; a dead-local sweep ends every interface edit, because an unused local rejects the object.

## 10. Evidence from humans and verification aids

- **Browser checklists**, not open questions: for every browser-only fact, the steps, the persona, and the expected strings, owned by a named human in `TODO.md`.
- **One statement, one grid** for anything a human runs in an external console: `check_name | result | detail` with PASS/FAIL per row; setup scripts are not evidence.
- **A single content source, one direction of flow:** the agent flags, the human adds to the source, the user adopts; no shortcut writes content into the reference layer.
- **Persona shims** stand in for the impersonation the MCP lacks, where sail cannot reach: an interface not yet on a page, or a persona with no local account. On a published page, a sail session as the persona is the stronger check (§12). A shim is a byte copy of the deployed interface with counted substitutions (`loggedInUser()` → `touser("x")`, or the membership rule swapped for a mirror taking `ri!isMember`), rendered, then deleted and confirmed absent. **Truth-table rules** prove gates and compositions: a throwaway rule mirroring the expression with one input per term, evaluated across every combination, then deleted. **Flip-render-restore** proves hidden branches: change the default to the hidden branch in a probe copy, render, restore, verify the restored source byte-identical to the saved copy.

## 11. Live-agent demo operations

- **Agent execution runs live as the permanent default.** Every click test, every rehearsal, and every verification runs the real agent through the real process, and assertions are written against what that run actually shows — never against a fixture's recorded decisions, a count copied out of a TODO item, or a constant. A fallback that doubles as a test harness is neither: it tests the wrong seam (a fixture runs no process, so the agent node, its inputs, and the output read stay unexercised), it makes assertions stale by construction (a test that expects the fixture's four exclusions fails the day the live agent legitimately decides five, and the test is what is wrong), and it hides the wait (the fixture resolves instantly; how the screen looks during a live run's forty seconds is itself something the demo shows).
- **A deterministic fixture path exists only as break-glass**, controlled by a **named run-mode constant** with exactly three stated values, read off the constant's own description: the live mode; a staged rehearsal mode (the identical process with a recorded proposal standing in for the agent call and a per-stage pause, written to the run row and read back through the same seam, so it exercises the real path); and the instant fixture (no process, the stored proposal served directly). Any other value is a silent half-state — the agent-path screen renders because the value is not the fixture, and the agent never fires because it is not live — so the valid values are the whole contract. The constant replaced an on-screen "proposal source" selector: a visible fixture switch is not sayable in front of a client, so the mode is an operator setting changed in Designer and the screen shows no trace of it in any state, verified by rendering both.
- **The switching policy is stated, not improvised.** The constant stays on live permanently. Switching to the fixture is permitted in exactly one circumstance — the demo-morning live-agent check fails for a demo-critical beat — by the operator, and the talk track does not pretend otherwise if it is used. Nothing routine flips it: not tests, not rehearsals, not "just to be safe". The fixture gets the same surface as the live path, not a lesser one (a run value is built from the check results and fed to the same card), so a fallback in the room does not look like one.
- **The fallback evolved into a product path, and the break-glass stayed in the code.** The preferred demo-morning fallback later became the deterministic route the agent's proposal is a diff against — the standard plan, tailored by hand — plus saved artifacts open in tabs before the room fills: a completed run, a pre-generated document, screenshots for every AI beat. That fallback is a complete product path and reads as one, so the governance story survives intact and only the diff beat is lost. The constant and the fixture branch remain for the one circumstance above; the runbook confirms the mode rather than setting it.
- **Rationale.** Demoing canned output as if it were an agent destroys credibility the moment anyone asks a question the recording cannot answer; a live failure in an executive room destroys it too. Both are avoided by building the fallback, naming it, giving it the same surface, and governing when it is used — rather than improvising on the morning or, worse, quietly testing through it until nothing in the build has been proven live.
- See `examples/deterministic-validation-gauntlet.md` for the seam and gauntlet the fixture passes through, and §5 for the runbook it belongs to.

## 12. Persona-scoped verification

Worked example: `examples/persona-verification-walkthrough.md`. The tool is in `toolchain.md` §12; the identity rules are in `CLAUDE.md` §6.

- **One isolated sail data directory per persona**, named for it (`~/.sail-<persona>`) and passed with `--data-dir` on every command. Claude Code's shell does not carry environment variables from one command to the next, so the flag, not `SAIL_HOME`, is what keeps a command on the right account. The default directory stays empty, so a forgotten flag fails with "no session found" [S26].
- **Personas need local Appian accounts.** Per sail's login help, its password login works only for local accounts, so an SSO-only identity cannot log in; the one SSO path imports the designer instead. Decide in Phase 0 which personas get local-password accounts (`BUILD_PLAN.md`, Personas).
- **The operator logs each persona in once, and the session persists.** The login reads the password from the environment, in the operator's own terminal. The session lives in the data directory until `logout` or the site's own session timeout [S25]. A session never handles a password: a missing or rejected persona session is reported and handed back to the operator. Sessions are machine-local and never recorded in the repo. Each session's preflight discovers the `~/.sail-*` directories on the machine it runs on and reports each username as live or expired (`CLAUDE.md` §2, step 9). The operator's step-by-step procedure, covering the local-account prerequisite, the commands, re-login after expiry, and what never to do, is in `GETTING_STARTED.md` §1, *Persona sail logins — step by step*.
- **Every observation states its account** — "as `<persona>` via sail: …" — in the response, the build log, and `Closeout.md`, because nothing on screen says whose view it is [S32].
- **Verification reads the YAML where the listing is incomplete.** The listing is for addressing. Grid rows, tag values, milestone details, and ordering are read from `<site>-ui-concise.yaml` [S7].
- **Writes are verified by reload and by the app's own attribution.** Navigate to the record or page and read it fresh, then confirm the activity entry naming the acting user, rather than trusting the submit's output [S13].
- **Designer-versus-persona diffs are deliberate:**
  1. Import the designer into a throwaway directory with `--from-devmcp`.
  2. Load the same pages as each persona's baseline.
  3. Diff the stored YAML after normalising the component ids the server mints per render.
  4. Delete the directory — never `logout`, which revokes the Dev MCP's own session [S31, S32].

## 13. Demo dry-run

- **Before a showing, sweep every persona through every page and action path via sail, and diff what each sees against the expected visibility matrix.** The matrix is the Personas section of `BUILD_PLAN.md` made concrete: per persona, the pages, values, and actions that must and must not appear, including masked values and status-driven bands. The sweep replaces the manual click-through for content and behaviour, which a persona's session reads and drives [S5, S10, S13, S32]; geometry is still checked in the browser.
- **Sweep surfaces, not screens.** Read every surface that shows a record type as each persona: dashboards, record lists, record views, related-action forms, and exports where reachable. A restriction implemented on one surface does not reach the others. This is how a delivered demo was found leaking a restricted record's masked fields, in clear, on its record-list page to a persona, after every designer-scoped check had passed. From the design seat every surface shows real values, so the surfaces agree and nothing looks wrong [S32, S33].
- **It runs after the last build change before a showing, not on the morning**; the demo-morning runbook stays at three items (§5). Writes during a sweep follow the demo-data rules (`CLAUDE.md` §12), and are reverted and verified like any other write.
