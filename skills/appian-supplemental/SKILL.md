# Appian Supplemental — measured facts and working method

**Version 2026-09-24.** The vendor pack's path follows Appian's current install layout, and the pack now loads as the `appian` skill beside this one. This version also carries the 2026-09-22 promotion: a flow looping back into an XOR gateway that has already fired never re-activates it, so loops return to a script node. The 2026-09-21 version promoted the sail evaluation: record-view action sets are verifiable per persona, site-reachable start forms are drivable end to end, ordinary forms show a button's disabled state, and the Dev MCP and runtime MCP servers are named by role.

> Template copy. Install at `~/.claude/skills/appian-supplemental/SKILL.md` (user level, so every build on the machine loads it). Project-specific facts never go in this file; they go in the build's CLAUDE.md or its project skill. Grow it only through the promotion gate below.

Everything here is environment-general: true of the platform, the Dev MCP, or Appian development practice regardless of project. Facts marked **(measured)** were established empirically on a live instance; the ritual on a new instance is re-verify-then-trust, never assume-then-debug. Project-specific conventions (data models, vocabularies, brand palettes, prefixes, status values) never live in this file — they live in each project's CLAUDE.md or project skill.

**Promotion gate — an entry is added ONLY when all five hold.** (1) **Measured, not suspected**: the error, readback, or render is in hand; a single surprising observation is a candidate in the project's build log until confirmed by reproduction or deliberate re-test. (2) **Survives the noun test**: stateable with zero project nouns; if it needs the project's vocabulary to be true, it is a project fact. (3) **Earns its context cost**: contradicts the docs or the pack, or cost real time — never a restatement of documented behavior; this file is the delta layer, not a mirror. (4) **Rule-shaped**: the trap AND the working form; instance-config-dependent facts carry the "(measured); re-verify per instance" tag. (5) **Contradictions named**: anything superseding the pack or a docs page says which and where. On promotion the project file keeps at most an application pointer — one home per fact, always.

**Promotion process — structural, not event-driven.** Promotion failed historically not at capture but at transfer, because it ran "when it felt warranted." Three rules make it self-enforcing: (1) **Promotion is part of every session close-out, never a separate campaign.** Every close-out includes a line — "Promotion candidates: N found; promoted / listed / none" — so the session that discovers a finding classifies it while it is in context, with no lag between finding and filing. (2) **The build-log promotion checkpoint is a gate, not a note.** A session that touches promotion refuses to call itself complete if the checkpoint lags the log tail by more than one session — self-auditing instead of memory-dependent. (3) **Parked debt carries a trigger condition, never "later."** Any deferred promotion or cleanup names the defined moment that fires it (e.g. "before the next project's portable-core split"), so post-development means a date-shaped event, not never.

## 1. Precedence and evidence (ABSOLUTE)

**A capability is present if something on this instance uses it. It is absent only if you have tried it here and it failed. "I searched the documentation and found no component for it" establishes nothing.** The component reference describes the documented general surface, not this environment, which carries tier-gated features, plug-ins, and file-format behaviour no docs page enumerates.

Precedence order when asking "can this environment do X":
1. **A working example on this instance.** Find it (`listApplications` → `listInterfaces`/`listApplicationObjects` → read the expression), quote the mechanism. Outranks everything below, including a docs page that appears to say otherwise.
2. **Tier- and feature-specific documentation** for the capability you now know exists.
3. **A test you run here** — the smallest thing that would prove it.
4. **The general component surface.** Weakest; never sufficient for a negative conclusion.

- A negative claim in a build log or TODO must name the evidence that produced it ("tried here, failed, here is the error"), never "the docs do not mention it".
- **Worked example, and the reason this rule exists:** a SMIL SVG rendered broken on an agent waiting screen; a docs search found no animated SAIL component and the conclusion drawn was "nothing animates here." Wrong: another app on the same instance had been animating a waiting screen the whole time with `a!imageField(images: a!documentImage(document: cons!<GIF>), size: "FIT")` — an animated GIF through the ordinary document-image mechanism. `a!documentImage` animates fine; SVG/SMIL specifically does not. One `listInterfaces` call would have found it.
- **Where a specific worked example and a general prohibition conflict, follow the worked example and PROVE IT BY RENDER** (established on sorting: `a!sortInfo()`'s page prohibits dictionary-array sorting; the Function Recipes' `todatasubset(array, a!pagingInfo(sort:…)).data` form is correct, proven by render).
- **When copying a mechanism from a working counterexample, copy its configuration too, and change one thing at a time afterwards.**
- **Docs establish what a parameter IS, not what this environment CAN DO.**
- Load the applicable Dev MCP plugin skills before any object work (Appian's `appian` skill, whose references are in `~/.claude/skills/appian/references/`) and consult the docs-search MCP for anything uncertain. Never guess parameter names. Project files override the pack and docs only where explicitly stricter; this file supersedes the pack where it records a measured correction.

### What the Dev MCP transport does to data (measure, do not assume)
- **`uploadDocument`'s `content` is string-typed and round-trips through UTF-8** — bytes above `0x7F` double in size; **binary assets (GIF, PNG, XLSX) cannot be created over MCP** and must be added by hand in Designer. Confirm a hand-added binary arrived intact by reading `document(id, "size")` against the local file BEFORE wiring anything to it — that separates "feature broken" from "file corrupt". (measured)
- **`updateConstant`/`createConstant` do NOT enforce the constant's declared type.** JSON number `0` into a TEXT constant returns 200, stores a Number, reads back happily — and Designer cannot open the object at all (HTTP 500). Always read a constant back and check the JSON *type* of `value`: `"value":0` on a TEXT constant is a defect, `"value":"0"` is correct. (measured)

## 2. UI work: mandatory grounding

Binding before ANY edit that creates or modifies interface layout, styling, or visual design — including a one-line width or colour change:

1. Load the frontend-design plugin guidance first (`~/.claude/plugins/marketplaces/claude-plugins-official/plugins/frontend-design/skills/frontend-design/SKILL.md`).
2. Read the relevant pack references before editing. Every layout edit: `interface-generation-checklist.md` plus the file for EACH layout in play (`layouts/columns-layout-instructions.md`, `layouts/sidebyside-layout-instructions.md`, `layouts/card-layout-instructions.md`, `layouts/pane-layout-instructions.md`, `layouts/section-layout-instructions.md`, `layouts/header-content-layout-instructions.md`, `layouts/form-layout-instructions.md`, `layouts/tab-layout-instructions.md`, `layouts/wizard-layout-instructions.md`). New interface: add `interfaces.md`, `sail.md`, `ui-patterns.md`. Rich text with links/colour/truncation: `components/rich-text-instructions.md`. Before done: `sail-verification-checkpoint.md`. Where a named file is absent or the pack doesn't cover the question, substitute docs-search and say you did. Cite no path you have not just listed.
3. Any uncertainty about parameter semantics, width allocation, wrapping, or component interaction goes to docs-search BEFORE the edit, and the documented answer is stated in the response. "It renders in the component tree" is not evidence a keyword is accepted; "accepted keyword" is not evidence it is usable in this position.
4. Every summary of UI work separates verified from unverified. Tree and harness prove structure (component order, colour values, requested widths, error-free evaluation); they carry no geometry — no pixel widths, line breaks, overflow, focus/hover, or link colour against site accent. Those are browser-only checks and must be listed as such. Never describe a layout as confirmed on harness evidence alone.
   - **AND THE TREE WILL LET YOU REPORT A LAYOUT THAT DOES NOT EXIST, so read the ATTRIBUTE, never the item count.** Worked example, measured: a rich text field built as `{item, char(10), item, char(10), item}` renders as three separate text entries in the tree **whether it stacks or collapses**, because `char(10)` is data, not layout. Set `preventWrapping: true` on that field and it renders as ONE truncated line — the docs are explicit that *"each paragraph or list item will truncate to a single line"*, and a `char(10)` inside a rich text value IS a paragraph break. Counting three items in the tree and reporting "stacked" is reading structure and claiming geometry; it shipped a broken cell past a render check and a written close-out. **The tree DOES expose `preventWrapping` per field** — so this one is checkable without a browser, and the check is the attribute. Generalise: when a parameter's whole job is to change geometry, verify the parameter's value, not the shape of the content it governs.
   - Related trap from the same family: `preventWrapping` is documented as incompatible with `"MINIMIZE"`-width side-by-side items, and it turns overflow into an ellipsis rather than a wrap — so it is the wrong tool for anything that must stay fully legible, and the right one only for a genuinely single-line cell.
5. Every generated interface goes through the pack's interface generation checklist and `validateExpression`/`testInterface` (`diagnostics.error: null`) before it counts as done.

## 3. Dev MCP mechanics and limits

- **GROUP MEMBERSHIP ADMINISTRATION IS NOT AVAILABLE OVER THE DEV MCP, THOUGH GROUP CREATION IS.** Measured: `createGroup` succeeds and the group appears in `listGroups`, but `addGroupMembers`, `getGroup` and `listGroupMembers` all return **HTTP 403 "Group not found or access denied"** — including against long-existing groups the same account lists successfully, which is what proves a surface-wide permission boundary rather than a propagation lag or a bad name. **Plan for it: a group created over MCP is EMPTY, and a site gated on it is invisible to everyone** — hand "add the first member" to a human in Designer explicitly, rather than discovering it when the page renders blank.
  - Two mechanics measured alongside it: a GROUP-typed constant takes the group's **NAME**, not its UUID (`value: "<Group Name>"` succeeds where the UUID fails with "Group not found"); and a freshly created group is briefly invisible to other calls, so a first attempt may fail purely on timing — re-list before concluding anything.
- **Objects outside an application are effectively unfindable over MCP** — nothing lists them, no lookup by name; `getExpressionRule` returns the same 403 for "does not exist" as for "is not a rule". Designer CAN search by name: an orphaned object is a thirty-second fix there, an unbounded hunt here.
- **`getObjectDependents` is the only reverse index** — finds objects an application does not list, and is the working substitute where `listAgents`/`getAgent` fail (returns the agent as an `AI_AGENT` dependent with its UUID). (measured)
- **A zero-byte document is not creatable** — seed files need real bytes and therefore a real job.
- **A `createProcessModelNode` that FAILS VALIDATION MAY still have created the node — check before retrying.** The call returns HTTP 500 (`Error creating node: Process Model contains errors/warnings: …`), which reads as a rejection, but the failure is not reliably a rollback: a `WriteRecordsWithEvents:400` failure left the node persisted with the payload as sent, while a `Non-nullable input ACP(s) … must not be null` failure on a Send E-Mail node left nothing behind. **Both outcomes occur, so never assume either.** Call `getProcessModelNode` first: if the node exists, recover with `updateProcessModelNode` (or delete it) — a blind retry fails with `Node with id N already exists` and leaves an invalid node in the model; if it does not exist, re-issue the create. Note that `data` is a FULL REPLACEMENT of the data section, so a recovery call must resend every input, not just the one being fixed. (measured, both branches)
- **WHERE A COMPONENT IS CONSTRUCTED IS PART OF WHETHER IT IS VALID — not just how.** Three measured instances, one rule: some components read variables that only exist while a specific parent is evaluating them, so building them anywhere else fails.
  - **A record action item cannot be built in a local variable.** `local!actions: a!flatten({a!recordActionItem(...)})` passed to `a!recordActionField(actions:)` fails the object validator with `Unresolved reference(s): recordAction!openActionsIn, recordAction!visibilityRefreshCounter`. Construct the items INLINE in the `actions:` parameter; compute the conditions that select them as locals instead. (measured)
  - **Related-action shortcut ORDER is not author-controlled.** A record view's `relatedActionShortcuts` accepts an ordered list and does not honour it — the readback returns the RECORD TYPE's own action order. Reorder on the record type (a Designer step; no MCP call reorders record actions) or accept the order you have. (measured)
  - **Consequence worth planning for: actions rendered by the record header are invisible to `testInterface`**, which evaluates only the view's own expression. The action set itself is verifiable per persona through the sail CLI, which lists the actions a record view offers to the account that reads it (measured: 29 actions for the design account and 26 for a persona on the same record; sail evaluation S32, `examples/persona-verification-walkthrough.md`). How the set changes with record status remains unmeasured. A visibility expression that throws still hides its action silently (§4). Weigh that against the convenience before moving actions out of a view.
- **AN OPTIONAL INPUT CAN BE ADDED TO A SHARED INTERFACE RULE WITHOUT TOUCHING ITS CALLERS — omitted inputs arrive NULL, not an error.** Measured: a `tooltip` input was added to a KPI-tile rule with four existing seven-argument calls on a separate, already-signed-off screen; that screen re-rendered with `diagnostics.error: null` and unchanged output. The widely-repeated "interface rules require every declared parameter to be passed" is true only of a **zero-argument** call to a rule that declares inputs (`rule!Foo()` fails); it is not true of a partially-argumented one. This matters because the over-broad version makes people edit ratified objects out of caution they do not owe. **The real risk is silence, not failure:** a null arriving where a boolean `showWhen` was expected hides a component without erroring, so add the input with a defaulting read (`a!defaultValue(ri!new, <safe>)`) and the old callers keep their old behaviour exactly.
- **`updateSite(pages:)` IS A FULL REPLACEMENT AND REGENERATES EVERY PAGE'S URL STUB.** Adding one page by resending the existing list changed the untouched pages' `webAddressIdentifier` values (e.g. `7K2G7Q` → `hDGI5A`), so any bookmark, deep link or documented URL into that site breaks. Resend the full list — omitting pages deletes them — but expect new stubs and re-check anything that hardcodes one. (measured)
- **Metadata is not the object's state** — `getDocument` can report `extension: null` where runtime `document(doc, "extension")` returns a value; resolve at runtime, never by believing the readback. (Same class as column widths, §7.)
- **A generated record type's Record List column configuration is not exposed over MCP** — default columns (raw FK integers) until set in Designer. Nothing errors.
- **Grid data binding, corrected rule:** grids over record data bind `data:` DIRECTLY to the record type, fully UUID-qualified — REQUIRED where native search, refresh, export, or per-column user filters are needed. The query-into-a-local pattern (`a!queryRecordType(...).data`) applies only to grids/components over assembled or joined non-record data. (Supersedes the older blanket "always query into a local" guidance. If a record-bound grid fails MCP validation in a new environment, re-probe before assuming either pattern.)
- **All record/field references fully UUID-qualified**: `'recordType!{<rtUuid>}<Name>.fields.{<fieldUuid>}<field>'` — NOT the datatype URN.

### Validation and testing
- **`validateExpression` evaluates BOTH branches of an `if`** (guarded-`1/0` probes are worthless), returns errors only, never values.
- **Test inputs are LITERALS for `testRule` AND `testInterface`** — an expression passed as input renders as though empty, silently. Query-dependent objects are verified through a wrapper interface, which does evaluate references.
- **Keyword strictness varies by validator, and the gaps ship broken objects silently:** object validators (`createExpressionRule`, `createInterface`) reject unknown keywords; `createSite` and `addRecordTypeAction` do NOT — a visibility/security expression with a wrong keyword (e.g. `a!isUserMemberOfGroup(groupsToCheck:…)`; the real parameter is **`groups`**) evaluates with the argument missing, typically returns false, and silently hides what it was meant to gate. Function keyword typos can no-op without error. The MCP validator rejects undocumented FUNCTIONS outright.
- **`validateExpression` IS NOT A KEYWORD CHECK, AND THE RENDERED TREE IS NOT A PARAMETER LIST.** Three measured instances of the same shape: `contentsWidth` on `a!headerContentLayout`, `truncateText` on `a!gridColumn`, and `shouldWrap` on `a!sideBySideLayout` — each appears in the component's own rendered tree, each is accepted by `validateExpression` with `hasErrors: false`, and each is rejected by the OBJECT validator (`Unrecognized Keyword …`). Only the object validator is authoritative; an attribute you can read back is not necessarily one you can set. The consequence is design-level, not cosmetic: `shouldWrap` would have let a side-by-side reflow, and without it a `width: "MINIMIZE"` sibling starves the flexible item beside it — with `preventWrapping` on, that overflow becomes a silent ellipsis rather than a visible break. When a layout cannot reflow, branch in the EXPRESSION on whatever actually drives the fit.
- **Therefore visibility and security expressions are verified BEHAVIOURALLY, never by validation alone:** read the stored expression back, confirm the keyword, then click as a member and as a non-member. Nothing automated distinguishes "hidden by rule" from "hidden by broken rule".
- **Expression rules validate at save time with no ContentService and no `env!`** — a bare `getpdftext()`, a record query in the body, or `a!callLanguageModel` cannot live in one; probes of this class are throwaway interfaces.
- **Design tooling caps one evaluation at 5 seconds; `testInterface` tolerates longer** — the interface route is the only legal and measurable home for real model calls.
- **`testProcessModel` cannot pass a RECORD-TYPED parameter, so any model whose parameter is a record value is not exercisable end to end over MCP.** The `inputs` map is marshalled into an `a!map()` of LITERALS: a string value is quoted, never evaluated (`"=a!update(...)"` arrives as Text and the Write Records node rejects it with `Each item within the input "Records" must be a record data type. Received: Text`), and a nested object whose keys carry the UUID-qualified field syntax breaks the map construction itself (`Invalid operator 'open_brace'`). **A third shape is the dangerous one: a nested object with PLAIN field-name keys marshals cleanly and reaches the node as a Map** (`Received: Map`) — so the process STARTS, runs every node upstream of the write, and only fails at the write itself. Nodes UPSTREAM of the write still run and their PVs read back, so the harness proves the pre-write half and nothing after it — and note what that means for a model whose upstream nodes compose from the payload: they compose from a value they could not read, producing a degraded-but-plausible result (measured: an event sentence composed with both of its real values missing, reading as a plausible generic sentence). If any such node WROTE rather than composed, the harness attempt would have left a garbage row behind. Options, in order: exercise the branch that skips the write (cancel/empty path) as a non-regression check; mirror the post-write nodes' expressions in a throwaway expression rule with real values to prove the composition; and run it end to end — **through the sail CLI as a persona when the model's start form is reachable from a site** (measured: related-action start forms driven and submitted as a persona, each write confirmed by a fresh read of the record and its activity entry; sail evaluation S11, S13, S19, `examples/persona-verification-walkthrough.md`), otherwise in a browser checklist. Attended mid-flow tasks remain browser-verified until measured. Say which of the three was done — do not report a partial run as a path exercised. (measured, both marshalling branches)
- **`testRule` cannot pass a Date input** (arrives as an integer; `todate()` doesn't rescue; `date(y,m,d)` as input isn't evaluated). Embed `date()` literals in a harness expression; the runtime PV path is fine and is what ships.
- **Icon names are verified via docs-search before use** — a plausible-sounding invalid icon (`chart-line`) fails the whole interface at create time.
- **`a!wizardLayout` evaluates ONLY the active step** — type errors in steps 2..n save clean and fail on first Next; `testInterface` renders only the active step too. Any step beyond the first needs a companion verification interface mirroring its expressions with realistic values. Wrap values pulled from maps with `todecimal()`/`tointeger()`/`todate()` before arithmetic.
- **A GENERATED VERIFICATION HARNESS GOES STALE THE MOMENT ITS SOURCE CHANGES, AND IT FAILS SILENTLY AND POSITIVELY.** The companion-interface technique above produces an artefact that mirrors a screen; describing it as "generated from the source, so it cannot drift" is true only while somebody re-runs the generator. When they don't, the harness keeps evaluating to `error: null` **against a screen that no longer exists** — a green light for yesterday's build, which is worse than no harness, because a red one would at least be noticed. (measured: a step harness was still rendering a two-way heading five days after the source became three-way; nothing anywhere reported a problem.) **Tie the regeneration to the same change that edits the source** — a harness re-synced in the commit that changed the screen, never "next time we look at it" — and before trusting any harness render, check one string you know you changed actually appears in it. A harness is a mirror, and an unmaintained mirror shows the room as it was.
- **A STEP'S OWN PROPERTIES — `disableNextButton`, `validations` — ARE INVISIBLE TO BOTH ROUTES.** `testInterface` never reaches an inactive step, and a companion interface does not help either: it copies the step's CONTENTS into a form layout, so the `a!wizardStep` properties are not in it. A navigation gate is therefore unverified by every render you can run. Mirror the gate expression in a THROWAWAY EXPRESSION RULE with one boolean/text input per term and evaluate the truth table — allowed and blocked states both — then delete it. Cheap, exhaustive, and the only automated evidence a gate does what it reads like. On a wizard step, the button's actual disabled state stays a browser check. The sail CLI reports a button's disabled state on ordinary forms — `[DISABLED]` in its listing, and the flip in its diff when a selection enables it (measured: sail evaluation S16, `examples/persona-verification-walkthrough.md`) — but wizard steps are unmeasured.

## 4. Expression and SAIL measured traps

### Silent wrong answers — the call succeeds and the number answers a different question
- **`.totalCount` RETURNS `-1`, AND THE USUAL WORKAROUND DOES NOT SCALE — COUNT WITH AN AGGREGATION.** Re-measured on a 50,000-row table at `batchSize: 1`: every `.totalCount` came back **-1**, and a readiness screen confidently reported "Baseline rows -1, expected 50,000" in red. `count(a!queryRecordType(…, batchSize: 500).data)` and `a!forEach`+`sum` work only where the answer is under the batch size, so neither reaches a real table. **The tool that does is `a!aggregationFields` with a COUNT measure** — one row holding the number, no row transfer: `a!queryRecordType(recordType: …, fields: a!aggregationFields(measures: a!measure(field: …, function: "COUNT", alias: "n")), filters: …, pagingInfo: a!pagingInfo(startIndex: 1, batchSize: 1)).data`, then `index(index(…, 1, null), "n", 0)`. Filters apply to the aggregate exactly as to rows. Reserve `count(...)` for a list you already hold.
- **`count()` returns 1 on a list of DICTIONARIES** (what `a!fromJson` produces) — count through `a!forEach`.
- **`list = {}` compares ELEMENT-WISE** — `a!isNullOrEmpty` is the scalar test.
- **`tostring()` on a LIST joins it into one delimited string while `tointeger()` maps element-wise** — the joined value makes `wherecontains` a guaranteed miss.
- **A LOCALLY-SOURCED `a!gridField` IDENTIFIES ROWS BY POSITION, NOT BY YOUR KEY.** The rendered tree reports `identifiers: [1..n]`, so `selectionValue` must be a ROW INDEX; hand it a business key and it matches nothing — no highlight, no error, and `selectionSaveInto` still returns indices, so a screen can look wired and select nothing. Measured both ways on a three-row local list: `selectionValue: 2` renders `selected: [2]` and highlights; `selectionValue: 92` (a real id in the data) renders `selected: [92]` and highlights nothing. Where the selection must survive filtering, keep the business key in a separate variable and derive the index from it each render.
- **`index(map, "key", default)` CANNOT TELL "KEY ABSENT" FROM "VALUE EQUALS THE DEFAULT", so handing a function the WRONG MAP SHAPE degrades silently instead of failing.** Measured: a parse gate returned a WRAPPER — `{ looksJson, candidate, parsed }` — around the object a consumer wanted; the wrapper was passed straight through, every `index(wrapper, "<realKey>", {})` returned its default, and the consumer produced a full, plausible, entirely wrong result (a full multi-row result with none of the structure the payload actually carried) with no error anywhere. **A defaulted read is an assertion that the key is optional. Where it is not optional, assert the shape instead** — check one key you know must be present before using the map, or have the wrapper-returning rule expose the inner value under a name the caller cannot get wrong. Same family as the entries above: the call succeeds and answers a different question.
- The defence: check the question matches the claim before trusting the result. `-1` is not a count; a clean validation is not a correct keyword.

- **AN HTTP INTEGRATION'S "AUTOMATICALLY CONVERT … TO JSON" CAN SHOW CHECKED AND STILL SEND THE APPIAN TEXT RENDERING OF A MAP.** Measured on an integration configured over the Dev MCP, in this configuration:
  - Content Type JSON, the checkbox shown checked in Designer, body expression an `a!map(…)`.
  - The remote API received `[key:value,…,nested:[k:v]]` — Appian's text form, not JSON — and rejected it with a 400.
  - Appian raised nothing; the only signal was the remote's error quoting the body.

  This contradicts the Integration Object docs, which say a dictionary passed with JSON selected is converted automatically. **Working form: make the body expression return the finished JSON string** — `a!toJson(<full payload map>, false)` — with automatic conversion OFF and Content Type still JSON. Two sub-facts from the fix:
  - `a!toJson()` rejects a bare Text value; it needs a map, dictionary, CDT, record or list.
  - A JSON object key that is not a valid SAIL identifier (e.g. `"1"`) is built with `a!update(a!map(), "1", value)`, and `a!toJson` emits it as an object key.

  Prove the body by evaluating the same expression in a throwaway rule, not by reading the integration back (next entry). (measured)
- **AN INTEGRATION'S EXPRESSION PROPERTIES READ BACK OVER THE DEV MCP WITH LEGACY VERSIONED FUNCTION NAMES THAT DO NOT MATCH WHAT RUNS.**
  - **The rewrite:** sent `a!toJson(…)` / `a!fromJson(…)`; both `updateIntegration` and a fresh `getIntegration` return `a!toJson_17r1(…)` / `a!fromJson_19r2(…)`.
  - **Not evaluable as written:** an expression rule containing the readback text verbatim fails validation (`Rule 'tojson' has 1 parameters, but instead passed 2 parameters`), yet the stored two-argument call executed at runtime.
  - **Booleans too:** a boolean property set to `false` reads back `null`.

  **So a readback of an integration is not a copy of the integration.** Verify its expression by evaluating the as-sent text in a throwaway rule; verify flags visually in Designer; treat one live call as the proof. (measured)

### Queries
- **Always pass `fields:` to `a!queryRecordType()` and `a!queryRecordByIdentifier()`.** Without it they return the identifier ONLY and every other field is null — no error, correct row counts, working filters, blank screen. Include related-record fields in the same list. The single most expensive gotcha measured: it shipped an apparently-verified dashboard rendering empty against real data.
- `a!queryRecordType()` has no top-level `sort:` — sorting goes inside `pagingInfo: a!pagingInfo(sort: a!sortInfo(...))`, list of sortInfo for multi-key.
- **A DELIBERATE "RETURN EVERYTHING" DECISION EXPIRES WHEN THE DATA SET IT WAS REASONED ABOUT SPLITS, AND NOTHING FAILS WHEN IT DOES.** The rule is not "always filter": it is that a safeguard justified by *"returning all of it and returning the relevant subset are the same list today, so the safer one is free"* carries a hidden dependency on that coincidence. When a second category is added the two stop coinciding — and the code still returns a correct SUPERSET, so no test breaks, no error is raised, and the cost surfaces somewhere else entirely (measured: an unfiltered reference list handed to an LLM tool tripled the agent's reasoning steps and its runtime, with the query itself still returning in milliseconds). **Write the coincidence into the comment that justifies the decision** — "these are the same list while X holds" — so the day it ends is a search hit rather than a regression hunt. Same family as the two entries around it: a query returning MORE than was asked, with nothing complaining.
- **THE RECORD-VIEW VALIDATOR EVALUATES THE VIEW WITH ITS IDENTIFIER NULL, AND EVERYTHING FED FROM THAT IDENTIFIER MUST BE GUARDED — not just the obvious call.** `a!queryRecordByIdentifier()` ERRORS on a null identifier, and so does any `a!queryFilter(operator: "=")` whose `value` comes from `rv!record` or the view's rule input (`"value" must not be null or empty`). The failure is at SAVE time, not at run time: the view simply will not save, on a screen that renders perfectly under `testInterface` with a real id. Guard the whole block once — `local!hasId: not(a!isNullOrEmpty(ri!id))`, then `if(not(local!hasId), {}, a!queryRecordType(…))` — rather than each call. **The same nullness reaches related-action visibility expressions**, which dereference `rv!record` and are evaluated by the platform with no error surface at all: a visibility expression that throws does not report, it just hides the action. Null-guard those too, and verify them by clicking, never by validation (measured; see also the keyword-strictness entry — visibility expressions are the one place where two different silent-failure modes overlap).

### Types and functions
- **SIBLING LAYOUTS DO NOT SHARE A WIDTH OR TYPE VOCABULARY, AND THE VALIDATOR IS THE ONLY PLACE THAT SAYS SO.** Two measured instances, one rule: `a!sideBySideItem(width:)` accepts ONLY `"AUTO"`, `"MINIMIZE"` and `"1X".."10X"` — the named widths that `a!columnLayout` takes (`NARROW`, `MEDIUM`, `MEDIUM_PLUS`…) are rejected outright, on a layout that reads almost identically; and `union(list, {})` fails with *"Invalid types, can only act on data of the same type (Text, Any Type)"* because `{}` is Any Type, so the working distinct idiom is `union(list, list)`. **Never carry a literal across from a neighbouring component because it looked the same.** The validator names the legal set in its error, which makes this cheap to check and expensive to assume.
- **`min()`/`max()` over DATES returns Number (Decimal), not Date**; over an INTEGER list also Decimal (then `wherecontains` refuses it — wrap `tointeger()`). Take extremes over integer day offsets and index the Date list by position.
- **Date minus Date returns an Interval** (prints `21::00:00:00.000`) — wrap day counts in `tointeger()`.
- **`tointeger()` ROUNDS** — use `floor()` for whole units.
- **`trim()` strips spaces but NOT newlines.**
- **`search()` cannot test substring presence** — `len(substitute(haystack, needle, "")) < len(haystack)` is the working form.
- **`text(-130, "0")` prints `13-0`** — route signed counts through `abs()` plus a word.
- **`text()` NEITHER ROUNDS NOR GROUPS BEYOND WHAT YOU SPELLED OUT — it truncates, and it emits `N/A` when a number outgrows the format.** Two measured failures of the same function, both producing plausible-looking output: (1) `text(1.87005, "0.0")` returns **`"1.8"`**, not `"1.9"` — `text()` TRUNCATES to the format's precision, so `round()` to the target precision BEFORE `text()`, always; (2) `text(18700500, "#,##0.00")` returns **`"18700,500.00"`** — only as many thousands-separator groups as are LITERALLY written in the format are applied, and once the number outgrows them the call returns the string **`"N/A"`** (`text(2340000000, "#,###,##0.00")`). Write one group per magnitude you intend to support, one wider than the data's maximum. Same family as the `13-0` entry above: `text()` accepts the number and misreports it. (measured)
- **Carry the real Date for arithmetic and the formatted string for display, never one value for both** — `todate("…")` vs a real Date silently never matches; `text(<Date as text>, "yyyy-mm-dd")` returns an error STRING without erroring. Clock basis is probed per instance.

### Lists, empties, joins, ordering
- **`wherecontains()` against an EMPTY list THROWS** — guard every filter on a non-empty source. `a!forEach` over an empty list returns Any Type, which `wherecontains` rejects.
- **`index(list, <list of matches>, default)` returns ROWS; indexing a cell afterwards silently reads the wrong dimension** — wrap each row in `a!map(...)`.
- **Two representations of an absent Document; `a!isNullOrEmpty()` catches one** — `index()` on an empty typed Document list returns `-2147483648`, passing the null check and failing downstream.
- **`union()` is not an ordering primitive** — iterate a canonical sequence and drop empties, or sort explicitly.
- **Every join from a local list to a grid row needs `a!defaultValue(...)` with DISTINCT sentinels on both sides** (e.g. `-1` / `-2`) — a bare equality errors on Null vs Integer. Recurs on every screen filtering an assembled list per row.
- **Write every nullable comparison/aggregate null-safe** so screens render under any data state.

### Forms and state
- **In a multi-step form, NEVER save a list of Text** — `a!save(local!list, append(local!list, <text>))` destroys the form instance (back to step 1, all locals lost, no error). Hold state as a delimited scalar and derive: `local!xCsv: ";"` saved, `local!x: reject(a!isNullOrEmpty, split(a!defaultValue(local!xCsv, ";"), ";"))`, delimiters at both ends, never key from free text that could contain the delimiter. Appending a MAP to a list is fine. Empirical; root cause unknown. (measured)
- **An interface with UNUSED LOCALS is REJECTED** — a hidden `showWhen: false` field referencing them satisfies the compiler.

### Multi-record-type payloads (write-destroying trap)
- **`append()` onto a strongly typed record list SILENTLY DROPS rows of a different record type** — no error, `onSuccess` fires, the write does less than it claims. **`a!flatten({listA, listB, listC})` is the ONLY safe accumulator for a multi-record-type payload.**
- **A brace list is Any Type only if its members DIFFER.** A single-element brace list `{ 'recordType!X'(...) }` is homogeneous, types itself `List of X`, and is exactly as lethal as a typed `a!forEach` while looking safe. (This cost a build every launch it performed: nested appends onto a single-record brace list `{ parentRow }` silently discarded every child row.)
- **A write path is verified ONLY by exercising the actual control and counting persisted rows per record type.** Direct payload inserts validate shape and bypass the control's accumulator; reading the expression, a green save, clean `testInterface`, and a successful direct insert are all non-verification.

## 5. Row-level security: reads, keys, and diagnosis (ABSOLUTE)

- **Every readback in a row-secured app must state the account scope it ran under, or it can prove the wrong thing.** Record-level security filters `listRecordData`, `a!queryRecordType`, `.totalCount`, and every derived count — silently, with no marker distinguishing "absent" from "invisible to you". (Measured: a complete seed was diagnosed half-loaded, a Blocking TODO raised, and a reload proposed — all artifacts of the reading account's scope membership.)
  - Write the scope into the readback itself ("as <user>, member of <groups>"), never just the numbers.
  - Before concluding rows are ABSENT, re-read as a member of every scope, or prove absence another way (a PK insert that succeeds proves the id was free; an id gap does not prove deletion).
  - `min`/`max`/`count` over a secured record type are per-viewer, never a high-water mark.
  - Restore original memberships afterwards and say so.
- **NEVER allocate a primary or business key as `max(...)+1` over a row-secured record type.** The max is the max *you can see*; `a!writeRecords` UPDATES when the supplied key exists, so the collision is a **silent overwrite of another scope's data**, not an error. Let the source assign keys (AUTO_INCREMENT; omit the PK), take FKs from relationships, or mint from an unsecured type. (Measured: this overwrote another scope's seed row.)
- **Writes targeted by primary key succeed against rows the calling account cannot read; only reads are filtered.** Useful for restoring another scope's data; a trap if you assume invisible means absent.
- **TWO MCP SERVERS FOR ONE PLATFORM CAN COEXIST UNDER A SINGLE TOOL NAMESPACE WITH DIFFERENT EXECUTING IDENTITIES, AND TOOL NAMES DO NOT ANNOUNCE THEIR SERVER.** Before trusting any scoped read or any process you start, establish which server a tool belongs to and which identity it executes as; a naming-convention split between tool families (e.g. camelCase-unprefixed vs snake_case with a product prefix) is the usual tell, and the client's server listing may show only one of them. Under a foreign identity the failure is silent and green: row-secured reads return **empty** while PK-targeted writes still **succeed**, so a process completes, reports no error, and has read nothing — and anything downstream that reasons over that empty read (an LLM especially) will confabulate rather than fail. Diagnose by running the same read through a tool from each family, and by a control on data known to exist. **Supersedes the assumption in this section that a session has ONE identity: it warns that reads are filtered, but not that the identity can vary PER TOOL within one namespace.** (measured) **The fix is naming by role — `appian` for the Dev MCP, `appian-runtime` for the runtime server — so the two can never share a namespace.** Both failure shapes of a shared name were observed on one machine:
  - **The shadow:** the name carried only the runtime server's 10 tools, and the design tools were missing while its `ping` answered.
  - **The merge:** 167 tools under one prefix. It passes the design-tool check and is caught only by the tool naming style.

  Renamed by role, the two loaded separately: 157 and 10 tools. (measured; `reference/toolchain.md` §2, sail evaluation S34)
- **Never key demo assets to platform-assigned ids** — derived numbers change on relaunch; identify specimens by their properties.

## 6. Record events and audit trails

- **`a!automationId()` values: `NONE` 1, `RPA` 2, `AI` 3, `INTEGRATION` 4, `OTHER` 5, `AI_AGENT` 6** (Designer renders it "AI AGENT"; the spaced display name is NOT accepted by the function — pass the underscored token). `NONE` means *completed by a user*. **CORRECTION to the vendor pack: `references/record-events.md`'s automation table (1 = Robotic Task, 2 = Appian RPA, 3 = AI Skill) is WRONG and superseded by this entry.** The platform supplies the "System" actor string for a null user. Working pairings: real user + NONE; null user + INTEGRATION (external system); null user + OTHER (the process's own orchestration).
- **Only the Write Records NODE writes events; `a!writeRecords()` cannot** — event writes are process-model nodes. Parameters live on `internal3.write_records_to_source_23r3`, reachable once the node schema is fetched with the base record type as `referenceUuid`.
- **The events generator does NOT copy record-level security onto the generated Event History type** (despite its own description) — a scoped viewer reads every row through a direct query until the inheriting RELATED_RECORDS rule is added by hand and read back.
- **`AutomationType` does not render anywhere on its own** — a distinction a reader must SEE cannot ride on it; use two event types.
- **An ungated event-writing node FORGES audit rows.** A node placed downstream of a write still executes when that write failed — sequence is not a guard. With `PauseOnError: false` this silently produces events describing actions that never happened. Gate every audit write on the business write's success (XOR on the error PV), never merely after it. (measured)
- **Events can be written WITHOUT writing records** — construct rows in a script task, ordinary Write Records node, `CaptureEvents` FALSE, set user/timestamp/eventTypeId/automationTypeId explicitly. The only way to emit differently-worded events from one node. Never mint the PK.
- **The event `comment` field is the only working per-event detail field from the node — and only where commenting is disabled app-wide.** The documented "add a field" promise is Designer-only: the added field never appears in the node schema over MCP (HTTP 400 on send). Cap composed detail to the MEASURED column width (declared 4000 read back as VARCHAR(255) on the measured instance). (measured)
- **An event's detail sentence is COMPOSED AT WRITE TIME from values in hand, and frozen forever** — never derived at render time, never backfilled. The old value exists only before the write (a reader node goes BEFORE the write node); rendered views fall back to the event type's name for pre-sentence rows rather than reconstructing from current data. **The freeze extends to notes and every mutable field**: a note joins the sentence only when the after-value DIFFERS from the before-value. Compose with a fixed category vocabulary and fixed priority for the length budget, so the identifying half is never the trimmed half.
- **Audit coverage is defined by a WRITE-PATH CENSUS, not by adding events where they seem useful.** Enumerate every write path and classify: **business** (user changing data — logs), **maintenance** (seeders, bulk re-dating — NEVER logs), **pre-record** (before the record exists — nothing to log against). **Maintenance machinery logging is a correctness defect — it forges a trail of edits nobody made**; an audit trail is worth its worst row.

## 7. Column widths and schema changes (ABSOLUTE)

- **CREATING a column applies `length`. ALTERING one does NOTHING, silently, and every readback lies about it.** `addRecordTypeField(length: n)` produces a real VARCHAR(n). `updateRecordTypeField(length: n, updateTable: true)` returns 200, bumps the version, and leaves the physical column untouched — as do Designer type flips. `getRecordType` then reports the *requested* width, not the real one. **The only way to widen a column is DROP AND RECREATE.** (measured, repeatedly)
- **A width verification is valid only if the probe writes through the same path production uses** (for record apps: `a!writeRecords` via a Write Records node — throwaway process model, `PauseOnError: false`, errors mapped to PVs, driven by `testProcessModel`). Any historical width claim tracing to an ALTER is invalid until re-proven by write.
- **A truncation cap in an expression must EQUAL the measured column** — below silently clips, above fails the write.
- **Drop-recreate is surgery**: the new field gets a NEW UUID and the drop NULLS every row **including rows your account cannot see** (restore from the seed generator, not a readback). Repoint every reference by UUID — interfaces, rules, process nodes, **and record type user filters** (`sourceRef`, `relatedRecordDisplayField`; note `updateRecordTypeUserFilter` prepends the relationship UUID itself — pass the bare field UUID). Verify each by RENDERING it: **a dangling field UUID does NOT fail validation** — it saves clean and renders empty.

## 8. Documents and templating

- **The template and the payload are ONE CONTRACT and move together** — neither half can be validated against the other by any automated check. Regenerate the template OUTSIDE Appian; read the contract before EITHER side changes. A payload element without its directive renders nothing; a directive without its element renders an empty table.
- **A replacement template is uploaded as a NEW VERSION of the existing document, never a new document** — the constant points at the uuid, so a new version needs no repointing. Two same-named files in a folder cannot be told apart later; if they coexist, disambiguate by size and creation time and delete the loser.
- **Generation is provable by EXISTENCE AND SIZE only** — Success returned, document exists, byte size exceeds the template's. Literal `${…}`/`#list` text surviving, empty loop tables, branding, page breaks, pagination are BROWSER-ONLY checks, stated explicitly. A wrong loop path returns Success and an empty table.
- **`doc` binds to the XML DOCUMENT NODE** — template paths run `doc.<rootElement>.<child>`; a payload rooted at `<doc>` fails with 0 nodes matched.
- **Two palette nodes labelled "DOCX From Dynamic Template"; the bare one is deprecated** — use `DOCXDocumentFromTemplateWithImgSizeOptions`.
- **The DEPLOYED node's parameter names win over the plugin README, always** — read them off the node.
- **Independent PDF converters failing identically on the same DOCX makes it a property of the document** — DOCX is the deliverable; keep any PDF leg behind an XOR.
- **`getDocumentText`/`getDocumentContent` may return HTTP 501** — the smart service's ErrorMessage and the file's byte size are then the only oracles without a browser. (measured; re-verify per instance)
- **Word merge fields cannot render line breaks reliably** — model multi-line content as LINE-ITEM LOOPS, never a scalar with newlines.

## 9. Process models, writes, sites

- **A single Write Records node writing record types on DIFFERENT data-source handles fails as a SILENT TOTAL NO-OP** — process COMPLETED, `error: null`, zero rows written for EVERY type in the payload, including the ones whose handle was fine. `a!flatten` is the correct accumulator (§4) and does not rescue it. **One Write Records node per record type, chained; wire `ErrorOccurred`/`Error` on every business write; gate downstream nodes on write success.** Isolated by measurement: two record types sharing one handle write correctly from a single node, so the trigger is the handle split, not multi-type payloads. Contradicts the node schema's own "If writing multiple record types in Records, events can only be captured for one", which presents multi-type writes as generally supported. **`PauseOnError: false` with an unwired `ErrorOccurred` makes a failed write indistinguishable from a successful one** — the run still reports COMPLETED. (measured)
- **Write Records' `RecordsUpdated` returns the generated primary key** (enables open-then-update), **but its ORDERING is not guaranteed — never join children positionally off it**; match on natural keys read back from the parent write.
- **A record-typed value inside an Any Type PV is LOST** (indexes Null; write rejects). Any PV carrying records through a map must be typed Map.
- **Only ONE smart service may run in an interface `saveInto`, and `onSuccess` accepts only `a!save()`/`a!httpResponse()`** — `a!writeRecords` cannot be chained inline to feed one write's key into the next. Multi-step writes: one call with nested related records (relationship must show `updateBehavior: "CASCADING"`) or a process model with chained nodes. The onSuccess variable is **`fv!recordsUpdated`**, not `fv!newRecords`.
- **`a!startProcess` does not expose `fv!error` to `onError`** — only `a!writeRecords` does (the pack's contrary example fails validation). Write a self-contained failure message.
- **No screen can be shown AFTER a related action's process finishes**; `testProcessModel` refuses models containing user input tasks. **That refusal does not arrive as a clean message**: measured, `testProcessModel` returns a bare `Network error:` (repeatably, on retry) and `appian_invoke_process_model` returns HTTP 500 `An unexpected error occurred` — even when the model has none of the Any Type parameters that tool separately rejects. Both read like infrastructure faults and will send you hunting; check the model for an attended node FIRST. A model with a user input task mid-flow is browser-only, end to end. Say what will happen on the start form.
- **Appian's AND gateway waits for ALL INCOMING CONNECTIONS, not all activated ones** — an AND join downstream of conditional branches deadlocks when a branch isn't taken. For "wait for all of N optional branches," route every branch to a single End node (a process stays active until every live flow ends). Reserve AND for the split.
- **Subprocess node inputs are PV NAME MAPPINGS, not expressions, and the API silently rewrites what you send**: `"myVar"` stores `pv!myVar`; `=pv!myVar` stores `pv!pv!myVar`; a literal stores NOTHING — all HTTP 200. Per-branch literals need their own PV with a default; computed values need a script node first. Always `getProcessModel` after writing a subprocess node and read every mapping back.
- **AN ACP BOUND IN A USER INPUT TASK'S FORM `inputMap` IS FORCED `required: true`, AND BOTH `required: false` AND OMITTING THE FLAG ARE SILENTLY IGNORED ON SAVE** — the readback shows `true` either way, all HTTP 200. The consequence is a runtime failure with a distinctive message: an ACP fed from a process variable that is legitimately null on the happy path (an error-text PV populated only on failure, say) throws **`Missing required value for ac!<name>`** when the task is submitted, on every successful run. **The fix is never the flag; it is to guarantee a value** — wrap the source in `a!defaultValue(pv!x, "<non-empty literal>")`. Prefer a non-empty default: an empty string may still read as absent to the required check, and a form that already null-defaults the input renders the placeholder invisibly anyway. (measured, both save forms)
- **Script task (`internal.16`) outputs go in `data.customOutputs`, not `data.outputs`** (outputs is for schema-defined named outputs, e.g. ErrorOccurred/Error on Write Records).
- **`site!` page references need BOTH UUIDs** — `'site!{siteUuid}Name.pages.{pageUuid}page'`; Appian rewrites the trailing identifier on save, so never guess it: create pages, read the site back, take page UUIDs from the response. Prefer `a!urlForSite` (fails loudly at save) over hand-built Tempo URLs (404 silently at a user).
- **`updateSite` REGENERATES EVERY PAGE UUID and web address identifier, including untouched pages** — after ANY updateSite, read the site back and re-point every stored reference, then test the linking interface.
- **Site page schema exposes no navigation grouping over MCP; page groups are Interface-page-only anyway** — RECORD_LIST pages sit flat. Gate related pages with the same `visibilityExpr`; keep top-level items to eight (Appian's stated ceiling). **`visibilityExpr` hides the PAGE, not just the tab** — treat it as access control; links to hidden pages do not work.
- **Configuring a record action does not surface it** — record views use `relatedActionShortcuts`; anywhere else place `a!recordActionField` deliberately; a grid's `recordActions` needs grid selection configured before `fv!identifier` works.
- **Send E-Mail (`internal3.sendemail3`) has four configuration traps, all of which fail late or silently.** (1) **`From` is a required non-nullable ACP** and is stored as a plain VALUE — `"Process Model"` — with an empty expression; omit it and the create fails with `Non-nullable input ACP(s) for unattended node(s) must not be null: From`. (2) **`IsHTML` must be TRUE for a body passed as text**: false switches the node to template mode and it then demands a `BodyTemplate` Document. Because the body is therefore rendered as HTML, separate lines with `<br>` and escape EVERY data value that reaches it. (3) **A bare `pv!` reference in `BodyHTML` fails with `begin 0, end -1, length <n>`** — wrap it in any function (`a!defaultValue(...)`) and it is accepted. (4) **An empty-string second argument to `a!defaultValue` in `BodyHTML` is silently dropped on save**, and the node then errors at runtime with `Too few parameters … expected at least 2 … found 1`; use a NON-EMPTY default and read the node back to confirm both arguments survived. (measured)
- **"FAIL FORWARD ON ERROR" IS A PER-SMART-SERVICE NODE INPUT, NOT A NODE PROPERTY — AND IF THE SERVICE DOES NOT OFFER ONE, THERE IS NO WAY TO CATCH ITS EXCEPTION.** The pause-on-error switch is declared by each service and named differently every time: `Pause On Error` (Write Records), `Pause Node on Error` (Query Database), `Pause Node on HTTP Error` (Call Web Service). **Read the node type schema first**: if no such input is listed, the service has no fail-forward mode. **The Exceptions tab is NOT the fallback and does not catch errors** — the docs are explicit that all its events (Receive Message / Timer / Rule) are *evaluated before the activity executes* and that if one fires *the activity is not executed at all*. It pre-empts an activity; it cannot handle an activity that threw. (It is also not exposed over the Dev MCP: neither the node payload nor `updateProcessModelNode` has an exceptions field.) So when a plugin service throws, the flow at that node stops and never reaches ANY downstream gateway — a gateway placed after it can never run, because a gateway is downstream and the exception happened upstream. **The only fail-forward for such a node is not to run it**: gate it out, move it to a separate process instance whose failure is isolated, or remove it. Note also that per Process Errors an error on an UNATTENDED node does not set the process to Paused by Exception — the process keeps whatever parallel flows it has — so an instance stranded this way can look merely "still running" rather than failed. (measured)
- **A send/notify node placed AFTER a Write Records node cannot roll back or block that write.** The write has already committed and Appian does not undo a committed write because a later node errors; the worst case is a paused instance at the send node with the data change durable. This is the reason to attach notifications as new downstream nodes rather than as extra work inside the write node. (measured pattern)
- **The Dev MCP process-model surface exposes NEITHER multiple-node-instances NOR recurrence.** The node schema has no MNI/loop field, so a per-item fan-out (one email per case, one call per row) must be built as an EXPLICIT LOOP: an index PV, a script node that seeds index and count, an XOR that compares them, the work nodes, an increment node, and a flow back to the XOR — always with a hard upper bound in the XOR condition so a bad count cannot spin forever. **The flow back must return to the SCRIPT node, never to the XOR** — see the next entry. Likewise `core.0` exposes no inputs and `updateProcessModel` has no recurrence field (`event.timer` is a DELAY timer, not a schedule), so a scheduled model is built complete and runnable over MCP and its recurrence is set on the start event in Designer. Say so rather than reporting the model as finished. (measured)
- **A FLOW RETURNING TO AN XOR GATEWAY THAT HAS ALREADY FIRED DOES NOT RE-ACTIVATE IT: THE INSTANCE SITS `ACTIVE` FOREVER, WITH NO ERROR AND NO PAUSED-BY-EXCEPTION.** Measured on an explicit loop built exactly as the entry above prescribed — seed → XOR(index ≤ count) → work → increment → back to the XOR. The first pass runs; the increment runs; the token then arrives at the gateway and nothing happens. The process is not paused, not errored, not completed: `testProcessModel` returns `status: "ACTIVE"` at timeout with the loop variables showing one completed pass (`idx: 2` against `count: 3`, trace `seed;take1=A;mid1;inc;`). **In production this reads as "the loop did one item and stopped"**, and because the instance never errors, the error-alert group is never notified and nothing in the audit trail says a run was abandoned.
  - **Working form, measured on the same probe in the same session:** loop back to the **script node** that takes the item, and put the continue/stop XOR **downstream of the increment**, so every gateway has exactly ONE incoming flow. Seed → XOR(any work?) → **take-item script** → work → XOR(written?) → increment → XOR(another?) → back to the take-item script. That ran all three iterations and returned `COMPLETED` in 6.5 s, trace `seed;take1=A;mid1;inc;take2=B;mid2;inc;take3=C;mid3;`.
  - **A script node re-entered by a loop-back fires every time** — only the gateway does not. Multiple incoming flows on a script node are fine.
  - **Isolate this before blaming the work nodes.** The same loop with Start Process nodes in it hung identically, which reads like a smart-service fault; removing them and re-running proved the smart services were never involved. A loop that stops after one pass is a gateway-re-entry suspect first.
  - **Contradicts** the explicit-loop recipe in the entry above (now corrected), which is also how Appian loops are commonly drawn. (measured)

- **Verification ceremony scope**: these are build-time and change-time rules. Routine operation of a working build (deleting a practice case, relaunching, running a demo) needs no readback, no row count, no wrapper — build-time rigor, run-time simplicity, and ceremony retires with the defect it was built for.

## 10. Layout and component facts

- **`a!sideBySideLayout` REJECTS a card as an item** — use `a!cardGroupLayout`.
- **A ROW OF CARDS IS LEVELLED BY THE GROUP, NEVER BY THE CARDS.** `a!cardLayout(height: "AUTO")` sizes EACH card to ITS OWN contents, so a row of cards with different body lengths — laid out as `a!columnsLayout` of `a!columnLayout`s, the obvious shape — ends ragged, and the tempting fix (pin every card to one fixed height token) trades ragged for either a crater of empty space or silently scrolling content. `a!cardGroupLayout` is documented as displaying "an arrangement of cards, with the same width and height", and ITS `cardHeight: "AUTO"` means every card takes the height of the TALLEST. Same keyword, opposite meaning, depending on which component owns it. Pass the cards DIRECTLY as `cards:` with no column wrapper; `cardWidth` is a FLOOR that `fillContainer: true` expands from, so pick a narrow token for a fixed small number of cards and let them fill. This is the second reason to reach for a card group, independent of the side-by-side rejection above. (measured)
- **FILLER IS A PIN YOU CANNOT GREP FOR.** Removing a `height` token and replacing it with margin/padding that reaches the same height is the SAME decision with the audit trail deleted. Measured over three versions of one card: pinned to a height token; "unpinned" by adding ~274px of enumerated margin to its rows to reach the same edge as its neighbour; reported as sprawl the moment its content grew by one row. A height pin at least announces itself to the next reader and to `grep`; spacing that exists to hit a neighbour's edge looks like typography and is found only by someone counting tokens against a comment. **Working form: a container's height is an OUTPUT of its content. When two neighbours must end level, that is the job of the component that levels them — `a!cardGroupLayout`, whose `cardHeight: "AUTO"` gives every card the height of the tallest — never of per-child spacing.** (measured)
- **A FIXED-WIDTH GRID COLUMN IS SIZED BY ITS WIDEST *WORD*, HEADER INCLUDED, AND `NARROW` HAS NO FLOOR** — so a column whose VALUES are short will break its own HEADER. Measured: an eight-character label over two- and three-digit values in a `NARROW` column rendered as "Duratio" over "n". The docs state both halves separately — a fixed-width column "will be at least as wide as the longest word in the column", and "`ICON` and `NARROW` do not have a minimum width" — but never draw the consequence: **the header is one of the words being measured, and in a numeric column it is usually the longest one.** Working form: **size a narrow numeric column by its LABEL, not its values.** Where the label is the long part, SHORTEN THE LABEL and put the full term in `helpTooltip`, rather than widening — widening spends width that the `AUTO` columns beside it need (see the entry below: what a fixed column takes, an AUTO column loses). (measured)
- **`AUTO` width means "whatever the fixed columns leave"** — it belongs to the column that tolerates any width; freed pixels go to the AUTO column, so a remedy naming the wrong column is worse than none.
- **`shadeAlternateRows` defaults true**; where shading and a STANDARD divider compete, weaken the divider (`borderStyle: "LIGHT"`).
- **A constrained `size` on `a!imageField` serves a RESIZED rendering — a resized animated GIF is one flattened frame.** Only `size: "FIT"` serves the file unresampled.
- **`helpTooltip`'s icon does not show with COLLAPSED label position**; `a!richTextDisplayField.tooltip` has no such restriction.
- **SAIL cannot restyle an input on focus** — CSS profiles are Admin Console, site-level, no focus state in the published property list, applied to every input at once.
- **Alignment vocabulary is per-component and not interchangeable**: rich text takes `LEFT`/`CENTER`/`RIGHT`; grid columns and button arrays take `START`/`END`; `a!tagField` has no `align` at all.
- **`a!kpiField` takes `align`, NOT `labelPosition`** — the pack's labelPosition examples are rich-text-in-cards, not KPI fields; never carry parameters across patterns.
- **`a!recordActionField` takes `style: "LINKS"` (plural) and has NO `labelPosition`.**
- **`addRecordTypeView.nameExpression` wants `="Summary"`** — the pack's `='"Summary"'` form fails as an unresolved reference.
- **Platform deltas never to fight when matching mockups**: no per-interface fonts (rich text size/weight for hierarchy; never font workarounds); no segmented progress component (colored glyphs or per-segment cards); no expandable/spanning rows and no row grouping in `a!gridField` (grouped reading = sectioned layout; flagged-items card section replaces expanded rows); no sticky footers, custom hover states, or exact pixel spacing. Page/header chrome comes from site-level branding — never build a brand bar inside an interface.
- **Chat components**: `a!recordsChatField` is native per-record chat on a record summary view, cloud-only, requires site enablement — verify on the target environment before assuming. No native cross-record chat: build with `a!chatField()` backed by an agent or `a!callLanguageModel` over Data Fabric queries; suggestion chips are buttons submitting preset prompts. Chat answers vary across runs (documented) — fallback screenshots for every chat beat are mandatory prep.
- **Idioms that consistently work**: `a!kpiField` or KPI-in-a-card, risk metrics first; statuses as colored `a!tagField` via `a!match`, never raw text; identifiers as `a!recordLink`, never plain strings; reference-data dropdowns from live records, never hardcoded.

## 11. AI agents (platform)

- **An Agent Studio record-data tool returns the backing record type's OWN fields only — no relationship traversal.** The Record Fields panel on the tool is **display-only, showing what comes back; it is not a picker** and cannot be extended to related types. Related context therefore costs either **one tool per record type (a query per type per run)** or **process-side assembly into a single text input** — prefer the latter for latency, deterministic wording, and because the query then runs in the process's security context rather than the agent identity's. **Why this is slow to diagnose:** the tool does not error; related fields are simply absent, which is byte-identical to an omitted `fields:` list (§4) and to a row-security filter (§5/§7). Symptom to recognise: the agent's own output says the context lacked the related data, and confidence collapses. (measured)
- **The documented default document tool is Semantic Search, not Read Full Document** — an instruction to read fully is load-bearing. Read Full Document ceilings: 50 pages text-only, 20 with images; per-run budget 75 documents / 50 MB.
- **Whether an agent iterates every element of a Document array is agent reasoning, not a platform guarantee** — say so explicitly in instructions and test with a distinctive requirement planted in the second document.

## 12. Working practices (portable method)

- **Naming pattern** (each project sets its prefix; the pattern is constant): record types `<PREFIX> <Entity>` singular; interfaces `<PREFIX>_<context><Purpose>` camelCase; rules/constants `<PREFIX>_<purpose>`/`<PREFIX>_<PURPOSE>`; groups `<PREFIX> <Scope>`, runtime groups under `<PREFIX> Users`.
- **Security baseline**: never `All Users` viewer on business data; Administrators (design) segregated from runtime groups; row-level scoping defined ONCE on the anchor record type(s), inherited everywhere via RELATED_RECORDS — never per-interface filtering, never restated conditions; no credentials or secrets in SAIL or sample data.
- **Data fabric purity for data-fabric demos**: 100% record types — never a CDT, never a data store entity, not even to satisfy a smart service that wants one (e.g. Export DSE to Excel is off the table; enumerate record-native alternatives). One stray CDT in the object list undercuts the demo's own argument and is what a technical reviewer looks for.
- **Deterministic sample data**: static values, no `rand()`/`now()`/`today()` in seeds — identical across re-evaluation. Regenerate by script, never hand-edit rows; any scripted duplicate of an in-app rule stays behaviorally identical to it.
- **Shared logic implemented ONCE** as a single expression rule used by every consumer, with variation as a parameter — never duplicated inline, never a second rule.
- **Structural rule**: 360s are record types with views and related actions, not bespoke interfaces; portfolio/list pages are site pages backed by the record type.
- **Two presentations of hierarchical data, distinct jobs, never mixed**: flat sortable/filterable grid (repeated parent values down columns are correct — they power filtering and export) and a grouped sectioned reading view.
- **Legacy → modern transform order** (verify each): headerContentLayout + brand header; KPI row of the domain's risk metrics; FK numbers → relationship traversal; plain-text status → colored tags + date-risk coloring; identifiers → recordLink; re-validate to `diagnostics.error: null`.
- **Agent-generated objects are drafts pending human review**; field-setting documented with `TODO-CONVERTER:` comments, side-effects with `TODO:`.
- **Live over fixtures**: rehearsals and click tests run the real agent path; assertions target the live run, never fixture recordings. Fixtures are break-glass for a failed demo-morning check, nothing else.
